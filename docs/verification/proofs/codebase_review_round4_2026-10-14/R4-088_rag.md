## (a) Empty re-index left the previous generation searchable

- **Root cause:** `index_document` returned `[]` at the `if not records:` early return
  *before* the delete for `(session_id, document_source)` ran. Truncating a file to zero
  bytes kept its old chunks searchable.
- **Fix (`pipeline.py`):** the early return is gone. The delete SQL is a named local
  (`delete_sql`) used by the same `_replace_and_insert` transaction path: advisory lock →
  DELETE → insert only when `records` is non-empty. The no-acquire test-double fallback
  issues the delete via `db.execute` when there is nothing to insert. `rows` initializes to
  `[]`, so audit/search-cache invalidation still run for the empty generation.
- **RED:** `R4-088_red_bce.txt` — `test_empty_reindex_deletes_previous_generation_only_for_its_source`
  fails `assert 1 == 0` with "empty re-index left the previous generation" (old generation
  still in `context_chunks`).
- **GREEN:** same test passes on real `machina_test` (H-DB):
  - previous generation count 0 after empty re-index,
  - a sibling source and another session's same-named source survive (adversarial boundary),
  - the warmed search cache does not resurrect the deleted generation.
- **Test:** `tests/test_fm5_consistency.py::test_empty_reindex_deletes_previous_generation_only_for_its_source`.

## (b) `split_code` detached decorators; single-symbol files lost `symbol`

- **Root cause:** the definition regex included `@...` as an alternative, so each decorator
  line matched as its own "definition" and produced its own chunk; and the structured path
  only ran when `len(matches) > 1`, so a single-definition file fell back to `split_text`
  and lost `symbol` metadata entirely.
- **Fix (`chunker.py`):** matches are grouped — runs of decorator matches attach to the
  following definition; the chunk starts at the first decorator while `symbol` stays the
  definition signature. A trailing decorator with no definition is kept as its own chunk
  (never dropped). The structured path now runs for `definitions` (≥1 definition).
- **RED:** `R4-088_red_bce.txt` — decorated-def chunk started at `def alpha` (not
  `@functools.cache`); single decorated file produced `['@deco', 'def only']`; single plain
  file produced `[None]` symbols.
- **GREEN:** `tests/test_rag.py::TestChunker::test_split_code_attaches_decorators_to_their_definition`
  (multi-decorator + two decorated defs + no standalone `@` symbol chunk),
  `test_split_code_single_decorated_definition_stays_whole`,
  `test_split_code_single_plain_definition_keeps_symbol_metadata`.
- **Regression:** existing preamble/alias tests and `test_fm5_chunker.py` property tests green.

## (c) `split_markdown` treated `#`-lines inside fences as headings

- **Root cause:** every line was matched against `_MD_HEADER` with no fence state; the
  compiled `_CODE_BLOCK` regex existed but was never used.
- **Fix (`chunker.py`):** `_CODE_BLOCK` is replaced by `_FENCE` (one delimiter line, 3+
  backticks or tildes) and a line-level tracker: a fence opens on the first delimiter,
  closes only on a same-character, at-least-as-long, info-string-free delimiter, and an
  unclosed fence masks to EOF. Fence lines are content; heading matching is skipped while
  inside a fence.
- **RED:** `R4-088_red_bce.txt` — headings became
  `{'Title', 'this is a comment inside a fence', ... 'this is a comment inside a fence > Real heading'}`,
  tilde fences produced `'not a heading'` paths, unclosed fence produced `'still code'`.
- **GREEN:** `test_split_markdown_ignores_headings_inside_fences`,
  `test_split_markdown_tilde_fences_also_mask_headings`,
  `test_split_markdown_unclosed_fence_masks_to_eof` (body keeps `Title > Real heading`;
  fenced code stays whole inside its section).

## (d) Dual retrieval-branch failure was indistinguishable from "no matches"

- **Root cause:** `HybridSearch.search` collapsed both `return_exceptions` into `[]` with
  only a log line (`"Hybrid search degraded: one retrieval branch failed"` — also wrong for
  the both-failed case); callers (the `search_documents` tool) rendered a confident
  "No results found".
- **Fix (`search.py`):** new typed `SearchUnavailableError(RuntimeError)` (defined in
  `rag/search.py` so the rag package's `machina.core` import ratchet — ceiling 15 — is
  untouched). When both branches raise, the method logs, emits a
  `rag_search_unavailable` audit event, and raises with the two error type names in the
  message. One surviving branch keeps today's behavior: its evidence is returned with
  `retrieval_degraded=True`. Through the tool, the existing catch renders
  `ToolError("Error searching documents: both retrieval branches failed ...")` — no
  `tools/rag.py` edit needed; an actually-empty index still renders "No results found".
- **RED:** `R4-088_red_d_pytest.txt` (pre-fix collection: the typed surface does not exist);
  `R4-088_red_d_probe.txt` — behavioral probe: both branches raise, search `returned: []`.
- **GREEN (adversarial + H-DB):**
  - `tests/test_deep_rag_scope.py::test_both_retrieval_branches_failing_raises_instead_of_empty`
    (SQL-boundary failure injection on the controlled double; typed raise).
  - `tests/test_deep_rag_scope.py::test_single_branch_failure_still_returns_degraded_evidence`
    (guard: single failure must NOT raise).
  - `tests/test_rag_quality.py::test_real_db_distinguishes_empty_index_from_dual_branch_failure`
    (real `db_pool`: same session answers `[]` while empty, raises `SearchUnavailableError`
    when both retrieval queries fail with `asyncpg.PostgresError`; embedding-space scan still
    passes through the real DB).
  - `tests/test_rag_quality.py::test_search_tool_renders_unavailable_distinct_from_no_results`
    (the tool renders `ToolError` for the outage and keeps "No results found" for a true miss).

## (e) repomap cache: write-only sha256 / overclaiming docstring

- **Root cause:** `lookup` compared only `(mtime, size)`; the stored digest was never
  verified, so a same-stat rewrite (mtime preserved, same size) served stale inventory
  parses forever. The docstring meanwhile claimed content-hash semantics.
- **Choice:** verify the digest on lookup (rather than renaming the class — callers import
  `ContentHashCache` from three other modules outside this lane's write scope:
  `repomap/scan.py`, `repomap/__init__.py`, `tools/repomap.py`). Now the name is truthful.
- **Fix (`repomap/cache.py`):** `lookup` requires an entry digest, short-circuits on stat
  change, then reads the file bytes and compares sha256 before returning the parsed tuple;
  mismatch → miss → caller re-reads and `store()` re-records. Docstring and module docstring
  state the actual cost (one bounded read per lookup; parsing only is skipped). `scan.py`
  comments corrected to match ("files parsed this pass"; retry runs re-hash).
- **RED:** `R4-088_red_bce.txt` — `lookup` returned stale `(1, ['os'], False)` after an
  mtime-preserving same-size rewrite; rebuild kept `files_scanned=0` and `pkg.a: ['os','pkg']`.
- **GREEN:** `tests/test_repomap.py::test_lookup_rejects_stale_digest_even_when_stat_matches`,
  `::test_rebuild_detects_mtime_preserving_rewrite` (`files_scanned == 1`, `re` present, `os`
  gone). Existing zero-parse tests (`test_repeat_with_cache_is_zero_work`,
  `test_cache_survives_to_disk`, `test_self_map...`, `test_v1_repomap_tool.py`) stay green:
  cache hits still parse zero files. `R4-088_probe_e_diag.py` shows build1=606 parsed,
  build2=0, build3=0.
- **Residual:** a file written by a *concurrent* process between store and lookup now
  legitimately counts as one re-parse; under the shared worktree one full-suite run tripped
  `test_self_map_completes_in_seconds_with_zero_repeat_reads` (files_scanned=1) — a
  concurrent pytest process (PID observed) was writing the tree. 3 consecutive re-runs were
  fully green, and in CI (single writer) the check is deterministic.

## (f) `_hard_split` looped forever for `chunk_size <= 0`

- **Root cause:** `_hard_split` never guarded its bound; with `max_chars <= 0` the cursor
  cannot advance (`start = end`), so `split_text(".", chunk_size=0)` spins forever.
  `_force_split` had the mirror gap: `size=0` raised a bare `range()` ValueError and
  `size<0` silently returned no chunks.
- **Fix (`chunker.py`):** both helpers raise `ValueError(f"chunk size must be positive, got
  {size}")` / `ValueError(f"max_chars must be positive, got {max_chars}")` before any loop.
- **RED:** `R4-088_red_f_pytest.txt` — the guard test's subprocess
  `TimeoutExpired: ... timed out after 30 seconds` (hang reproduced).
- **GREEN:** `tests/test_chunker_overlap.py::test_nonpositive_size_guard_never_hangs`
  (subprocess so a regression FAILS instead of hanging the suite; covers `_hard_split`,
  `_force_split`, and `split_text(chunk_size=0)` for 0/-1/-10) and the hypothesis property
  `test_hard_split_pieces_are_lossless_and_bounded` (positive bounds: lossless, every piece
  0 < len ≤ max_chars).
