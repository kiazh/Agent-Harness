## Bullets

### (a) same-id re-resume guard — `ui/src/app.ts` (`switchTo`, ~L401)

- **Probe/root cause:** re-resuming the *visible* session (`/resume <current>`,
  picking the current row in `/sessions` or `/search`) routes through
  `session.resume` → `App.switchTo(session, history)`. `switchTo` cleared the
  transcript and replayed the fetched history, which cannot contain the
  in-flight turn: live deltas vanished and the running tool's card was dropped,
  so its later `tool.complete` found no card and was discarded
  (`transcript.ts` tool.complete only settles known ids).
- **Fix:** early-return when `session.id === this.current?.id`; refresh session
  metadata via `updateSession` and render, keeping the local transcript (the
  visible session's authoritative record).
- **RED:** `live streamed text survives the same-id re-resume` (mid-turn switch
  shows only the header). **GREEN:** text + running tool card survive; the
  completion reconciles and renders once (focused run green).
- Regression guard `(a2)`: a *different-id* switch still clears and replays the
  fetched history (passes pre- and post-fix).

### (b) hidden turn-failure notices — `ui/src/tail.ts` (`message.complete`, L121)

- **Probe/root cause:** `bufferHiddenEvent` dropped every block of the
  completing turn (`filter(block => block.turnId !== event.turnId)`). Failure
  notices are not persisted to history, so they were deleted at
  `message.complete` and never replayed on switch-back.
- **Fix:** keep `notice` blocks (errors/stopping/ownership notices) across
  completion; assistant/tool blocks still collapse to the canonical text.
- **RED:** `the failure notice survives completion and switch-back` (screen
  shows only the header). **GREEN:** the error notice replays as a system
  notice when switching back.
- Note: all notice kinds are kept, not only `error` — deliberate superset; they
  are bounded by `MAX_TAIL_BLOCKS` and none are persisted to history.

### (c) composer outer window — `ui/src/components.ts`

- **Probe/root cause:** `windowAroundCursor` silently clipped body rows beyond
  the composer budget (no `↑/↓ N more` marker), and `ComposerInput.handleMouse`
  mapped screen rows to editor-native rows without the window start, so clicks
  landed `start` rows above the row the user pointed at.
- **Fix:** new `composerWindow(rows, budget, popupHeight)` returns the rendered
  rows **plus the mapping** (`bodyRows`, `start`, `contentRows`,
  `markerAbove`); when clipping is needed it reserves ≤2 rows for
  `↑ N more` / `↓ N more` markers (same format as the editor's own borders),
  counts only non-blank hidden rows, and keeps the cursor row visible. The
  budget now lives on `ComposerInput.windowRows` (set by `ComposerBox.setMaxRows`)
  so render and mouse hit-testing share one derivation. `handleMouse` maps
  body clicks through `start`/`markerAbove`, ignores marker rows, and keeps the
  popup mapping and picker-first behavior unchanged.
- **RED:** no marker (`hidden rows above the window are disclosed`) and
  click on the "line8" row put the cursor on line 1 (`1 !== 8`).
  **GREEN:** marker present; the same click puts the cursor on line 8.
- Edge rules: budget ≤ 2 keeps the cursor row without a marker (no room);
  blank editor border rows never justify a marker.

### (d) Ctrl+S via `matchesKey` — `ui/src/components/Form.ts` (L94, L242)

- **Probe/root cause:** both forms tested `data === "\x13"`; under the Kitty
  keyboard protocol the terminal encodes Ctrl+S as CSI-u `\x1b[115;5u`, so the
  save shortcut did nothing. `matchesKey(…, Key.ctrl("s"))` handles both the
  legacy control byte and Kitty (verified directly against pi-tui 1.0.0).
- **RED:** `Kitty ctrl+s saves` (actual `[]`). **GREEN:** Kitty save works in
  `TextForm` and `SecretForm`; legacy `\x13` still saves.

### (e) cobalt2/solarized selection contrast — `ui/src/design/theme.ts`

- **Probe/root cause:** non-codex selected rows painted `background()` (the
  skin's neutral surface) as ink over the accent fill. Cobalt2
  `#193549 on #0088ff` = **3.62:1**; solarized `#002b36 on #268bd2` = **4.08:1**
  — both below WCAG AA 4.5:1 (`R4-094_red_contrast.txt`).
- **Fix (token-level):** derive per-skin `selectionFill` (accent; codex keeps
  its own selection fill) and `selectionInk` — the surface colour when it
  already clears 4.5:1 (look unchanged for passing skins), otherwise pure
  black/white, whose better ratio is always ≥ 4.58:1. `selectedRow` /
  `selectionBar` consume the tokens; `selectionInk(name)` / `selectionFill(name)`
  are exported for token-level tests.
- **RED:** token missing / contrast below threshold. **GREEN:** every skin
  ≥ 4.5:1; cobalt2 → `#000000` 5.97:1, solarized → `#000000` 5.71:1
  (`R4-094_green_contrast.txt`); the rendered `selectionBar` paints the token.

### (f) `/mode revoke` copy — `ui/src/features/mode.ts` (L57)

- **Probe/root cause:** the FULL HOST activation notice advertised
  `/mode revoke`, which does not exist (`/mode` accepts
  ask|workspace|sandbox|full; revoke lives at `/approvals revoke`).
- **Fix:** copy now points at `/approvals revoke`.
- **RED/GREEN:** test asserts the notice matches `/\/approvals revoke/` and not
  `/\/mode revoke/`.

### (g) `/delegate` client budget — `ui/src/app.ts` (L205, L333)

- **Probe/root cause:** `App.request` used a flat 120 000 ms client timeout,
  equal to the orchestrator's `DELEGATION_TIMEOUT_SECONDS = 120.0`
  (`core/orchestrator.py:55`) that the gateway's `agents.run` enforces. A child
  run that reaches its budget aborts the RPC on the client clock at the exact
  moment the server is still serializing the timeout result.
- **Fix:** `agents.run` uses `DELEGATION_TIMEOUT_MS = 150_000` (> server
  budget); every other method keeps 120 000. The call site in `agents.ts` is
  unchanged (it already routes through `host.request`).
- **RED:** recorded timeout 120 000. **GREEN:** recorded timeout 150 000
  (> 120 000) for `agents.run` (the fake client records the third argument).

### (h) `/keys` allowlist — `ui/src/features/keys.ts` (L20–40)

- **Probe/root cause:** `KNOWN_KEYS` (used for `/keys set|clear` completions)
  listed `OPENCODE_API_KEY`, `CUSTOM_API_KEY`, `CUSTOM_BASE_URL`, which the
  gateway's `secrets.set` refuses (`_ALLOWED_SECRET_KEYS` =
  `PROVIDER_KEYS` + `MANAGED_ENV_KEYS`, `machina/gateway/features/secrets.py`;
  user-added providers are accepted only as `MACHINA_PROVIDER_<NAME>_API_KEY`).
- **Fix:** `KNOWN_KEYS` now mirrors the gateway allowlist exactly (10 provider
  keys + DATABASE_URL/SEARXNG_URL/MACHINA_MODEL); the comment records the
  source of truth and the derived provider-key shape.
- **RED:** `/keys suggests OPENCODE_API_KEY, which secrets.set refuses`.
  **GREEN:** every suggestion is in the gateway allowlist and every allowlisted
  key is suggested.
- Residual (not this lane): `OPENCODE_API_KEY`, `CUSTOM_API_KEY`,
  `CUSTOM_BASE_URL` are still consumed by provider specs
  (`core/provider/specs.py`, `factory.py`, `config.py`) and cannot be set via
  `/keys`; they need `.env` or `/provider add` today. Route to the R4-082/R4-093
  lanes if the allowlist should widen instead.

### (i) job prefix pagination — `ui/src/features/jobs.ts` (L8–36)

- **Probe/root cause:** `resolveJobId` looped on `nextCursor`, but the
  gateway's `jobs.list` has no cursor and never returns one
  (`gateway/features/jobs.py:65-81`; `job_store.list` = newest-first
  `ORDER BY created_at DESC LIMIT ≤500`). The loop was dead code and the
  `Too many jobs to scan (100 pages)` message was unreachable; with >500 jobs a
  miss reported `No job starts with …` as if the id did not exist.
- **Fix:** one bounded listing (`limit: 500`, no `cursor` param). If the prefix
  is not in the window **and** the window is full, the error is honest:
  `Showing only the newest 500 jobs; "<prefix>" was not found in that window.
  Use a full job id.` In-window prefixes still resolve exactly as before.
- **RED:** the 500-job miss produced the old false `No job starts with`. The
  updated `fm7-display.test.ts` W6 pin (was: "refuses an endless cursor chain",
  now: "scans one bounded listing, never a cursor chain") is likewise RED on
  the unfixed loop. **GREEN:** exactly one `jobs.list` request, no `cursor`,
  honest cap message; in-page prefix still resolves.

### (j) MCP OAuth cancel on transient failures — `ui/src/features/mcp-oauth.ts`

- **Probe/root cause:** after `mcp.oauth.start`, failure exits only cancelled
  the operation on the overall timeout or an explicit user decline. A
  retry-exhausted status failure, a failed login-link load, or a failed
  `start` abandoned the server-side operation/preview with a browser wait
  still pending.
- **Fix:** best-effort `mcp.oauth.cancel` on every post-review failure exit —
  `cancelOperation()` (clears the poll timer, sends `operationId`) for the
  transient/permanent status failure (L192) and the `mcp.oauth.url` failure
  (L218); `previewId` cancel on a failed `start` (L114). All `.catch(() =>
  undefined)`: cancel is best-effort, never masks the original error.
- **RED:** none of the three paths issued a cancel. **GREEN:** cancel with
  `operationId: op-1` (retry exhaustion and link failure) and
  `previewId: preview-1` (start failure); bounded at 3 status polls; terminal
  `cancelled/expired/failed` states still do not re-cancel.
