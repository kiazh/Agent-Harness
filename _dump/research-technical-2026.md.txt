19|## 1. PostgreSQL + pgvector for LLM Memory
20|
21|### 1.1 Architecture Overview
22|
23|AgentHarness uses PostgreSQL with pgvector as its primary memory store — embeddings live in the same rows as the data they describe, so a memory query is one SQL statement with ordinary `WHERE` filters instead of a fan-out to a second system plus the pipeline that keeps them in sync.
24|
25|### 1.2 HNSW vs IVFFlat: The Index Decision
26|
27|| Property | HNSW | IVFFlat |
28||---|---|---|
29|| Build time | Slow (10–30× slower) | Fast |
30|| Index size | 2–5× larger | Small |
31|| Query latency (p99) | 5–20ms @ 1M vectors | 12ms+ @ 1M vectors |
32|| Recall ceiling | High (0.96+) | Moderate (0.92 default) |
33|| Build on empty table | Yes (no training step) | No (needs data for k-means) |
34|| Handles incremental inserts | Good | Degrades, needs re-train |
35|| Memory during build | High | Low |
36|| Tunable at query time | `ef_search` (runtime) | `probes` (runtime) |
37|| Default for most workloads | **Yes** | No |
38|
39|**Recommendation: Default to HNSW for AgentHarness.** It is the correct choice for read-heavy agent workloads where recall matters and data arrives continuously. IVFFlat is only appropriate for bulk-loaded, mostly-static datasets or when memory is genuinely constrained.
40|
41|### 1.3 HNSW Tuning Parameters
42|
43|```sql
44|-- Production HNSW index for 1536-dimension embeddings (OpenAI Ada-002, text-embedding-3)
45|CREATE INDEX CONCURRENTLY idx_chunks_emb_hnsw
46|ON chunks USING hnsw (embedding vector_cosine_ops)
47|WITH (m = 16, ef_construction = 128);
48|
49|-- Runtime tuning per session or per query
50|SET LOCAL hnsw.ef_search = 100;  -- 40=default, 100=sweet spot for k=10-30, 200+=recall priority
51|```
52|
53|#### Parameter Reference
54|
55|| Parameter | Default | Production | What it trades |
56||---|---|---|---|
57|| `m` | 16 | 16 (32 for hard recall) | Higher = better recall, larger index, slower build |
58|| `ef_construction` | 64 | 128–200 | Higher = better graph quality, slower build |
59|| `ef_search` | 40 | 100 (60–80 live, 200+ rerank) | Higher = better recall, slower query |
60|
61|**Sizing formula:** Index size ≈ `rows × dimensions × 4 bytes` + `m × 8 × rows` (graph edges). A 5M × 1536-dim index is ~30 GB.
62|
63|### 1.4 Quantization Strategies for Memory Reduction
64|
65|#### Scalar Quantization (halfvec)
66|
67|```sql
68|-- Store as float32, index as halfvec (2-byte floats)
69|CREATE INDEX idx_chunks_emb_halfvec
70|ON chunks USING hnsw ((halfvec(embedding, 1536)) halfvec_cosine_ops)
71|WITH (m = 16, ef_construction = 128);
72|```
73|
74|- **2× storage reduction** with negligible recall loss
75|- Clear win for dimensions ≥ 512
76|- Faster index builds (fewer pages)
77|
78|#### Binary Quantization (bit)
79|
80|```sql
81|-- Store as float32, index as bit (1 bit per dimension)
82|CREATE INDEX idx_chunks_emb_bq
83|ON chunks USING hnsw ((binary_quantize(embedding)::bit(1536)) bit_hamming_ops)
84|WITH (m = 16, ef_construction = 128);
85|```
86|
87|- **32× storage reduction** (367 GB → 38 GB at 100M × 768-dim)
88|- Requires reranking step: fetch top-N candidates with Hamming distance, rescore with full vectors
89|- Works best on distributions with high bit-diversity; validate recall on your data
90|- Elasticsearch BBQ (with corrective factors) achieves 29× compression with recall@10 of 0.994
91|
92|#### When to Use Which
93|
94|| Strategy | Compression | Recall Impact | When |
95||---|---|---|---|
96|| Full float32 | 1× | None | < 10M vectors, memory available |
97|| halfvec | 2× | Negligible | 10–50M vectors, default choice |
98|| Binary (BQ) | 32× | 5–15% (recover via rerank) | 50M+ vectors, memory-constrained |
99|
100|### 1.5 Iterative Scans (pgvector 0.8+)
101|
102|```sql
103|SET LOCAL hnsw.iterative_scan = relaxed_order;
104|SET LOCAL hnsw.max_scan_tuples = 20000;
105|```
106|
107|Prevents the "not enough rows returned" problem when combining an ANN index with a restrictive `WHERE` clause. Without this, pgvector fetches top-k from the index first, then filters — potentially returning fewer rows than requested.
108|
109|**For AgentHarness:** Enable `iterative_scan` on any memory query that filters by `tenant_id`, `agent_id`, or `session_id`.
110|
111|### 1.6 Production Configuration
112|
113|```ini
114|# postgresql.conf — pgvector-tuned
115|shared_buffers = 8GB                    # 25% of RAM; HNSW index should fit
116|effective_cache_size = 24GB             # 75% of total RAM
117|maintenance_work_mem = 8GB              # Critical for HNSW index builds
118|work_mem = 32MB
119|max_parallel_maintenance_workers = 7    # Parallel index builds
120|random_page_cost = 1.1                  # SSD + many in-memory pages
121|```
122|
123|### 1.7 Hybrid Search Pattern
124|
125|```sql
126|-- Combine vector similarity with full-text search using RRF
127|SELECT id, content,
128|       ts_rank(content_tsv, query) AS text_rank,
129|       1 - (embedding <=> $1) AS vector_score
130|FROM chunks, plainto_tsquery('english', $2) query
131|WHERE tenant_id = $3
132|ORDER BY ts_rank(content_tsv, query) + (1 - (embedding <=> $1)) DESC
133|LIMIT 10;
134|```
135|
136|Hybrid search beats pure semantic search when users expect exact keyword matches. Use `pg_trgm` or `pg_bm25` for BM25 scoring.
137|
138|### 1.8 Common Pitfalls
139|
140|| Pitfall | Symptom | Fix |
141||---|---|---|
142|| `maintenance_work_mem=64MB` (default) | HNSW build 10–50× slower, OOM | Set to 8GB+ |
143|| Wrong operator class | Index ignored, seq scan | Match `<=>` with `vector_cosine_ops`, `<->` with `vector_l2_ops` |
144|| Filter without iterative scan | Under-filled results | Enable `iterative_scan` (0.8+) |
145|| IVFFlat on empty table | Useless clusters | Build after data loaded |
146|| No index rebuild after heavy updates | 3–5× latency degradation | Schedule weekly `REINDEX CONCURRENTLY` |
147|| Cold cache after deploy | p99 spikes | Pre-warm: `SELECT pg_prewarm('idx_name')` |
148|
149|### 1.9 Scaling Bands
150|
151|| Vectors | P50 | P95 | QPS | RAM | Strategy |
152||---|---|---|---|---|---|
153|| 1M | 3ms | 8ms | ~800 | ~6 GB | Default HNSW |
154|| 10M | 5ms | 18ms | ~500 | ~55 GB | Tuned HNSW + halfvec |
155|| 50M | 12ms | 40ms | ~280 | ~250 GB | HNSW+BQ + pgvectorscale |
156|| 100M | 28ms | 95ms | ~150 | ~500 GB | Dedicated vector DB or Citus sharding |
157|
158|**Single-node limit:** ~50M vectors with HNSW. Beyond this, use Citus for sharding or a dedicated vector database.
159|
160|### 1.10 Ingest Patterns
161|
162|```sql
163|-- Idempotent ingest via content hash
164|INSERT INTO chunks (document_id, content, content_hash, embedding)
165|VALUES ($1, $2, md5($2), $3)
166|ON CONFLICT (content_hash) DO NOTHING;
167|```
168|
169|Batch upserts with `ON CONFLICT DO NOTHING` are essential — naive per-row inserts exhaust connections fast. Use PgBouncer in transaction-pooling mode at 1:5 ratio (DB connections to application threads).

173|## 2. MessagePack vs Protocol Buffers vs JSON for Context Storage
174|
175|### 2.1 Format Comparison
176|
177|| Property | JSON | MessagePack | Protocol Buffers |
178||---|---|---|---|
179|| Schema | None (self-describing) | None (self-describing) | Required (.proto) |
180|| Size | Baseline (1×) | ~22–40% smaller | ~3–10× smaller |
181|| Serialize speed | Baseline | 3–10× faster | 5–20× faster |
182|| Deserialize speed | Baseline | 2–5× faster | 5–10× faster |
183|| Human-readable | Yes | No | No |
184|| Binary data | Base64 (+33% overhead) | Native | Native |
185|| Cross-language | Universal | Excellent | Excellent |
186|| Streaming | Line-delimited | Yes | No (length-prefixed) |
187|| Ecosystem maturity | Universal | Very high | High |
188|
189|### 2.2 Size Benchmarks
190|
191|For a typical agent message payload (30 records with mixed types):
192|
193|| Format | Size | vs JSON |
194||---|---|---|
195|| JSON | 7,951 bytes | 1× |
196|| MessagePack | 6,363 bytes | 0.78× (22% smaller) |
197|| Protocol Buffers | ~800–1,500 bytes | ~0.1–0.2× (80–90% smaller) |
198|
199|### 2.3 Token Efficiency for LLM Context
200|
201|The choice of serialization format directly impacts token consumption when sending context to LLMs. Research shows:
202|
203|- **TOON (Token-Optimized Numeric)** format achieves 40–60% token reduction vs JSON for structured data, with LLM interpretation accuracy matching JSON (100%).
204|- **CSV** is 2–3× more token-efficient than JSON for tabular data.
205|- **MessagePack** is 22% smaller than JSON but still requires base64 encoding for LLM context, negating some savings.
206|- **Protobuf** is most compact for storage/transmission but requires deserialization before LLM ingestion.
207|
208|### 2.4 AgentHarness Recommendation
209|
210|| Use Case | Format | Rationale |
211||---|---|---|
212|| Inter-agent messages (storage) | **MessagePack** | 22% smaller than JSON, faster parse, no schema migration needed, good cross-language support |
213|| Inter-agent messages (LLM context) | **JSON** (compressed) | LLMs need human-readable text; use minified JSON or TOON if token budget is critical |
214|| Database persistence | **JSONB** (PostgreSQL) | Native indexing, querying, GIN indexes on metadata |
215|| Wire protocol between services | **MessagePack** or **Protobuf** | MessagePack for flexibility, Protobuf if schema is stable |
216|| Caching layer (Redis) | **MessagePack** | 22% memory savings, faster serialization |
217|
218|### 2.5 Implementation Pattern
219|
220|```python
221|import msgpack
222|import json
223|
224|class ContextSerializer:
225|    """Dual-format serializer for agent context."""
226|    
227|    def to_storage(self, messages: list[dict]) -> bytes:
228|        """Serialize for inter-agent transport — compact binary."""
229|        return msgpack.packb(messages, use_bin_type=True)
230|    
231|    def from_storage(self, data: bytes) -> list[dict]:
232|        """Deserialize from inter-agent transport."""
233|        return msgpack.unpackb(data, raw=False)
234|    
235|    def to_llm_context(self, messages: list[dict]) -> str:
236|        """Serialize for LLM consumption — minified JSON."""
237|        return json.dumps(messages, separators=(',', ':'), ensure_ascii=False)
238|    
239|    def to_db(self, messages: list[dict]) -> str:
240|        """Serialize for PostgreSQL JSONB — standard JSON."""
241|        return json.dumps(messages, ensure_ascii=False)
242|```
243|
244|### 2.6 Common Pitfalls
245|
246|- **Protobuf schema evolution:** Adding fields is safe; removing fields or changing types requires careful migration. For rapidly-evolving agent message schemas, MessagePack is safer.
247|- **MessagePack `raw` vs `bin`:** Always use `use_bin_type=True` for correct string/binary distinction.
248|- **JSON in JSONB:** PostgreSQL JSONB adds ~20% overhead over plain JSON but enables indexing. Use it for metadata fields you query on.

252|## 3. ReAct Agent Loop Optimization
253|
254|### 3.1 The Canonical Loop Structure
255|
256|```python
257|async def agent_loop(
258|    goal: str,
259|    max_steps: int = 12,
260|    deadline_s: float = 60.0,
261|    max_tokens_total: int = 200_000,
262|) -> AgentResult:
263|    messages = [{"role": "user", "content": goal}]
264|    started = time.monotonic()
265|    tokens_used = 0
266|    last_calls: list[tuple] = []  # For no-progress detection
267|    
268|    for step in range(max_steps):
269|        # --- Check budgets BEFORE the call ---
270|        if time.monotonic() - started > deadline_s:
271|            raise TimeoutError(f"Deadline exceeded at step {step}")
272|        if tokens_used > max_tokens_total:
273|            raise RuntimeError(f"Token budget exhausted at step {step}")
274|        
275|        # --- Generate ---
276|        response = await model.generate(messages, tools)
277|        tokens_used += response.usage.input_tokens + response.usage.output_tokens
278|        messages.append({"role": "assistant", "content": response.content})
279|        
280|        # --- Natural exit: no tool calls ---
281|        if response.stop_reason != "tool_use":
282|            return AgentResult(answer=response.text, steps=step)
283|        
284|        # --- Dispatch tool calls ---
285|        for block in response.tool_calls:
286|            # No-progress detection
287|            call_sig = (block.name, json.dumps(block.input, sort_keys=True))
288|            last_calls.append(call_sig)
289|            if last_calls[-3:].count(call_sig) >= 3:
290|                raise RuntimeError(f"No-progress: repeated {block.name} 3×")
291|            
292|            try:
293|                output = await run_tool(block.name, block.input)
294|                results.append({
295|                    "type": "tool_result",
296|                    "tool_use_id": block.id,
297|                    "content": json.dumps(output),
298|                    "is_error": False,
299|                })
300|            except Exception as e:
301|                # Errors become observations, not exceptions
302|                results.append({
303|                    "type": "tool_result",
304|                    "tool_use_id": block.id,
305|                    "content": f"error: {type(e).__name__}: {e}",
306|                    "is_error": True,
307|                })
308|        
309|        messages.append({"role": "user", "content": results})
310|    
311|    raise RuntimeError(f"Step cap reached: {max_steps}")
312|```
313|
314|### 3.2 Stopping Conditions (Disjunction)
315|
316|The loop must stop on the **first** of these conditions:
317|
318|| Condition | Implementation | Typical Value |
319||---|---|---|
320|| `stop_reason != "tool_use"` | Natural exit | — |
321|| Step cap | `for step in range(max_steps)` | 12–20 (not 5–50) |
322|| Wall-clock deadline | `time.monotonic()` check | 60s |
323|| Token budget | Sum of input+output tokens | 200K |
324|| No-progress detector | Hash of last 3 `(tool, args)` tuples | 3 identical calls |
325|| Goal predicate | `hasToolCall("submit_final_answer")` | — |
326|
327|**Critical insight:** `generate calls = tool rounds + 1`. The +1 is the final round where the model has everything it needs and just answers. This is always there for an agent that finishes normally.
328|
329|### 3.3 Retry Patterns for LLM Calls
330|
331|#### Exponential Backoff with Full Jitter
332|
333|```python
334|import random
335|
336|class RetryBudget:
337|    """Per-task retry budget with token cap."""
338|    
339|    def __init__(self, max_attempts: int = 4, max_tokens: int = 500_000):
340|        self.max_attempts = max_attempts
341|        self.max_tokens = max_tokens
342|        self.tokens_consumed = 0
343|    
344|    def compute_delay(self, attempt: int) -> float:
345|        """Full jitter: random.uniform(0, cap)."""
346|        cap = min(2 ** attempt, 128.0)
347|        return random.uniform(0, cap)
348|    
349|    def should_retry(self, error: Exception, attempt: int) -> bool:
350|        if attempt >= self.max_attempts:
351|            return False
352|        if self.tokens_consumed > self.max_tokens:
353|            return False
354|        # Only retry transient errors
355|        return isinstance(error, (ConnectionError, TimeoutError, RateLimitError, ServiceUnavailableError))
356|```
357|
358|#### Error Classification
359|
360|| Error Type | Examples | Action |
361||---|---|---|
362|| **Transient** | 5xx, timeout, connection reset, rate limit (429) | Retry with backoff |
363|| **Fatal** | 4xx (except 429), auth failure, invalid config | Fail immediately |
364|| **Recoverable** | Tool returned unexpected format | Feed error to model as observation |
365|
366|#### Idempotency Keys
367|
368|```python
369|# Deterministic idempotency key — NOT uuid4()
370|idempotency_key = hashlib.sha256(
371|    f"{task_id}:{tool_name}:{canonical_args_hash}:{attempt_number}".encode()
372|).hexdigest()
373|```
374|
375|The `attempt_number` increments only after a confirmed transient error, never on network ambiguity.

377|### 3.4 Circuit Breaker Pattern
378|
379|```python
380|class CircuitBreaker:
381|    """Three-arm breaker: provider, tool, cost."""
382|    
383|    def __init__(self):
384|        self.arms = {
385|            "provider": BreakerArm(failure_threshold=5, cooldown_s=60),
386|            "tool": BreakerArm(failure_threshold=10, cooldown_s=30),
387|            "cost": BreakerArm(failure_threshold=1, cooldown_s=3600, cost_threshold=100.0),
388|        }
389|    
390|    def call(self, arm: str, fn: Callable, *args, **kwargs):
391|        if self.arms[arm].is_open():
392|            raise CircuitOpenError(f"{arm} circuit is open")
393|        try:
394|            result = fn(*args, **kwargs)
395|            self.arms[arm].record_success()
396|            return result
397|        except Exception as e:
398|            self.arms[arm].record_failure()
399|            raise
400|```

402|### 3.5 Streaming Architecture
403|
404|```python
405|async def stream_agent_loop(goal: str) -> AsyncIterator[AgentEvent]:
406|    """Yield events in real-time for SSE/WebSocket delivery."""
407|    messages = [{"role": "user", "content": goal}]
408|    
409|    yield AgentEvent(type="loop_start", data={"message": goal})
410|    
411|    for step in range(max_steps):
412|        yield AgentEvent(type="iteration_start", data={"number": step})
413|        
414|        # Stream model response
415|        async for chunk in model.stream(messages, tools):
416|            yield AgentEvent(type="thinking", data={"chunk": chunk})
417|        
418|        # Execute tools
419|        for tool_call in response.tool_calls:
420|            yield AgentEvent(type="action_start", data={"tool": tool_call.name})
421|            result = await run_tool(tool_call.name, tool_call.input)
422|            yield AgentEvent(type="action_complete", data={"tool": tool_call.name, "result": result})
423|        
424|        yield AgentEvent(type="iteration_end", data={"number": step})
425|    
426|    yield AgentEvent(type="complete", data={"text": final_answer})
427|```

429|### 3.6 Tool Failure Fallbacks
430|
431|```python
432|@tool
433|def search_database(query: str) -> str:
434|    """Search with graceful degradation."""
435|    try:
436|        result = db.query(query, timeout=5)  # Socket timeout at client level
437|        if not result:
438|            return "No results found. Try a broader search term."
439|        return f"Found: {result}"
440|    except socket.timeout:
441|        # Use ToolException, not string signaling
442|        raise ToolException("Database timeout. Will retry with cache backend.")
443|    except PermissionError:
444|        raise ToolException("Authentication failed. Try alternative query method.")
445|```
446|
447|**Key insight from production:** The fallback IS the system's intelligence about recovery. Returning "Tool failed" is useless. Returning "Tool failed because the query was malformed; try rephrasing the question" gives the agent something to work with.
448|
449|### 3.7 Common Failure Modes
450|
451|| Failure | Symptom | Mitigation |
452||---|---|---|
453|| Infinite tool loop | Same `search` query every step | Hash recent calls, refuse duplicates |
454|| Tool error cascade | One 500 leads to model panic and 6 retries | Surface errors as structured content |
455|| Context overflow | Step 12 exceeds 200K tokens | Summarize older tool results into scratchpad |
456|| Wrong tool picked | Model calls `search` when it should use `calculator` | Tighten tool descriptions, add few-shot examples |
457|| Hallucinated tool name | Tool not in registry | Validate name; return "no such tool" as tool_result |
458|| Premature final answer | Stops without checking | Add system prompt: "Verify with at least one tool" |
459|| Hallucinated observations | Model writes fake `Observation:` | Always use `stop=["Observation:"]` |
460|
461|### 3.8 Context Management
462|
463|```python
464|class ContextManager:
465|    """Keep context under control as the loop progresses."""
466|    
467|    def compress(self, messages: list[dict]) -> list[dict]:
468|        """Summarize older tool results to free context window."""
469|        if count_tokens(messages) < 100_000:
470|            return messages
471|        
472|        # Keep system prompt + last 4 exchanges
473|        system = messages[0]
474|        recent = messages[-8:]
475|        middle = messages[1:-8]
476|        
477|        summary = llm.summarize(middle)
478|        return [system, {"role": "system", "content": f"Summary of earlier work: {summary}"}] + recent
479|```

543|### 4.3 Routing Strategies
544|
545|| Strategy | How it works | Best when |
546||---|---|---|
547|| **Weighted pick** | Random selection weighted by provider capacity | Balanced load across providers |
548|| **Rate-limit aware** | Tracks RPM/TPM per provider, routes to least-loaded | Providers have strict rate limits |
549|| **Least busy** | Routes to provider with fewest in-flight requests | Variable latency |
550|| **Latency based** | Routes to provider with lowest recent p99 | Performance-critical |
551|| **Cost based** | Routes to cheapest provider that meets quality bar | Cost optimization |
552|| **Usage-based** (default) | Combines rate limits, latency, cost | Production default |

554|### 4.4 OpenAI-Compatible Interface Pattern
555|
556|```python
557|from openai import OpenAI
558|
559|class LLMProvider:
560|    """Unified interface across OpenAI, Anthropic, Ollama, OpenRouter."""
561|    
562|    def __init__(self, config: ProviderConfig):
563|        self.client = OpenAI(
564|            base_url=config.base_url,
565|            api_key=config.api_key,
566|        )
567|        self.model = config.model
568|    
569|    async def generate(
570|        self,
571|        messages: list[dict],
572|        tools: list[dict] | None = None,
573|        temperature: float = 0.0,
574|        max_tokens: int = 4096,
575|    ) -> LLMResponse:
576|        response = self.client.chat.completions.create(
577|            model=self.model,
578|            messages=messages,
579|            tools=tools,
580|            temperature=temperature,
581|            max_tokens=max_tokens,
582|        )
583|        return LLMResponse(
584|            content=response.choices[0].message.content,
585|            tool_calls=response.choices[0].message.tool_calls,
586|            usage=response.usage,
587|            stop_reason=response.choices[0].finish_reason,
588|        )
589|```

591|### 4.5 Fallback Chain Pattern
592|
593|```python
594|class ProviderPool:
595|    """Ordered fallback chain with health tracking."""
596|    
597|    def __init__(self, providers: list[LLMProvider]):
598|        self.providers = providers
599|        self.health = {p: True for p in providers}
600|    
601|    async def generate(self, messages: list[dict], tools: list[dict] | None = None) -> LLMResponse:
602|        for provider in self.providers:
603|            if not self.health[provider]:
604|                continue
605|            try:
606|                response = await provider.generate(messages, tools, timeout=30)
607|                return response
608|            except (TimeoutError, ServiceUnavailableError, RateLimitError) as e:
609|                self.health[provider] = False
610|                asyncio.get_event_loop().call_later(60, lambda: self._mark_healthy(provider))
611|                continue
612|        raise AllProvidersFailedError("All providers exhausted")
613|```

661|### 4.8 Semantic Caching
662|
663|```python
664|class SemanticCache:
665|    """Cache responses by semantic similarity to avoid redundant LLM calls."""
666|    
667|    def __init__(self, threshold: float = 0.92):
668|        self.threshold = threshold
669|        self.cache = {}  # embedding -> response
670|    
671|    async def lookup(self, messages: list[dict]) -> LLMResponse | None:
672|        query_text = messages[-1]["content"]
673|        query_embedding = await embed(query_text)
674|        
675|        for cached_embedding, response in self.cache.items():
676|            similarity = cosine_similarity(query_embedding, cached_embedding)
677|            if similarity >= self.threshold:
678|                return response
679|        return None
680|```

684|## 5. Agent Session Management and Fork Patterns
685|
686|### 5.1 LangGraph Checkpointing Model
687|
688|LangGraph's checkpointing system provides the foundation for durable agent sessions:
689|
690|```
691|Thread (thread_id) = Conversation or workflow execution
692|  ├── Checkpoint 0: Initial State
693|  ├── Checkpoint 1: After Agent Node
694|  ├── Checkpoint 2: After Tool Node
695|  ├── Checkpoint 3: After Synthesis Node
696|  └── ...
697|```
698|
699|Each checkpoint contains:
700|- **State values** — The full state dictionary (messages, tool results, custom data)
701|- **Metadata** — Timestamp, step number, parent checkpoint ID
702|- **Version info** — For state schema migrations
703|
704|### 5.2 Session Lifecycle
705|
706|```python
707|from langgraph.checkpoint.postgres import AsyncPostgresSaver
708|
709|# Setup (idempotent)
710|pool = AsyncConnectionPool(conninfo=DSN, min_size=2, max_size=20, kwargs={"autocommit": True})
711|saver = AsyncPostgresSaver(pool)
712|await saver.setup()  # Creates checkpoints, checkpoint_blobs, checkpoint_writes tables
713|
714|# Compile once, cache for process lifetime
715|graph = builder.compile(checkpointer=saver)
716|
717|# Run with thread_id
718|config = {"configurable": {"thread_id": "session-123"}}
719|result = await graph.ainvoke({"messages": [HumanMessage(content="Research topic")]}, config)
720|
721|# Resume after crash — pass None as input
722|result = await graph.ainvoke(None, config)
723|```
724|
725|### 5.3 Fork Pattern
726|
727|```python
728|# Get checkpoint history
729|history = [c async for c in graph.aget_state_history(config)]
730|
731|# Fork from an earlier checkpoint
732|fork_point = history[3]  # 4 steps ago
733|fork_config = {
734|    "configurable": {
735|        "thread_id": "session-123-fork",
736|        "checkpoint_id": fork_point.config["configurable"]["checkpoint_id"],
737|    }
738|}
739|
740|# Continue from the fork with different input
741|await graph.ainvoke(
742|    {"messages": [HumanMessage(content="Try the alternative approach")]},
743|    fork_config,
744|)
745|```
746|
747|**Use cases for forking:**
748|- **A/B testing** — Try different strategies from the same point
749|- **Debugging** — Reproduce and fix issues without losing previous work
750|- **Human-in-the-loop** — Pause, review, edit state, resume
751|- **Counterfactual evals** — "What if the agent had done X instead?"
752|
753|### 5.4 State Schema Design
754|
755|```python
756|from typing import TypedDict, Annotated
757|from langgraph.graph.message import add_messages
758|
759|class AgentState(TypedDict):
760|    # Reducer functions control how fields merge across nodes
761|    messages: Annotated[list, add_messages]  # Appended, not replaced
762|    question: str                             # Replaced
763|    context: list[str]                        # Replaced
764|    plan: list[str]                           # Replaced
765|    status: Literal["draft", "researching", "complete", "failed"]
766|    retry_count: int                          # Replaced
767|    final_answer: Optional[str]               # Replaced
768|    error: Optional[str]                      # Replaced
769|```
770|
771|**Critical rules:**
772|1. Keep state small and serializable — it's written to storage after every step
773|2. Never mutate state in place; return an update
774|3. Use `add_messages` reducer for message history (appends, doesn't replace)
775|4. Keep large blobs (files, audio) by reference, not by value
776|

778|
779|```python
780|from langgraph.types import interrupt
781|
782|# Pause before critical actions
783|graph = builder.compile(
784|    checkpointer=saver,
785|    interrupt_before=["send_refund", "delete_file"],
786|)
787|
788|# 1. Agent runs to the interrupt point

800|
801|```sql
802|-- Table sizes to monitor
803|SELECT thread_id, COUNT(*) as checkpoints 
804|FROM checkpoints 
805|GROUP BY thread_id 
806|ORDER BY checkpoints DESC 
807|LIMIT 20;
808|
809|-- Archive idle threads (30+ days)
810|SELECT cron.schedule(
811|    'archive-old-threads',
812|    '0 3 * * *',  -- Daily at 3am
813|    $$INSERT INTO checkpoints_archive SELECT * FROM checkpoints 
814|      WHERE thread_id IN (
815|        SELECT thread_id FROM checkpoints 
816|        GROUP BY thread_id 
817|        HAVING MAX(created_at) < NOW() - INTERVAL '30 days'
818|      ) $$
819|);
820|```

822|### 5.7 Checkpoint Retention Policy
823|
824|| Policy | Recommendation |
825||---|---|
826|| Checkpoints per thread | Cap at 2,000; archive older to cold storage |
827|| Event retention | Keep full ledger 90 days for audits |
828|| PII | Mask fields in state before checkpointing |
829|| Orphan threads | Reap after 30 days idle via cron |
830|| Backups | Non-negotiable — lost checkpoint table = lost product |

832|### 5.8 Multi-Agent Orchestration Patterns
833|
834|| Pattern | How it works | Best when |
835||---|---|---|
836|| **Sequential (Handoff)** | Linear pipeline, each agent processes output of previous | Deterministic workflows |
837|| **Supervisor** | Central manager routes to specialists, feedback loop | Dynamic planning, quality gates |
838|| **Concurrent** | Multiple agents work in parallel, results aggregated | Brainstorming, ensemble reasoning |
839|| **Group Chat** | Agents in managed conversation, manager coordinates | Debate, consensus-building |
840|| **Magentic** | Manager builds task ledger, adapts in real time | Open-ended complex problems |
