12|## 1. Why Memory Matters
13|
14|AgentHarness already has the skeleton of a memory system:
15|
16|- `ContextChunk` (in `ah/core/models.py`) stores typed records with embeddings,
17|  token counts, and access timestamps.
18|- `ContextManager` (in `ah/core/context.py`) provides CRUD, batch insert, and
19|  pgvector similarity search.
20|- `PromptAssembler` (in `ah/core/assembler.py`) assembles prompts within a
21|  token budget, with a `retrieved_chunks` parameter that is currently always
22|  passed as `[]`.
23|
24|What is missing is the **memory lifecycle**: what to store, when to consolidate,
25|how to score importance, how to forget, and how to retrieve across sessions.
26|Without these, the system is a passive log — not a memory.
27|

30|## 2. Short-Term vs Long-Term Memory
31|
32|### 2.1 Short-Term Memory (Working Memory)
33|
34|**Definition:** The content currently inside the LLM's context window during a
35|single inference call. In AgentHarness, this is the `messages` list built by
36|`PromptAssembler.assemble()` and passed to `provider.complete()`.
37|
38|**Characteristics:**
39|
40|| Property | Value |
41||---|---|
42|| Latency | 0 ms (already in prompt) |
43|| Duration | Single session |
44|| Capacity | Bounded by `context_budget` (default 8000 tokens) |
45|| Retrieval | Automatic — everything in window is visible |
46|| Failure mode | Context bloat, truncation, "lost in the middle" |
47|
48|**Current state in AgentHarness:**
49|
50|- `PromptAssembler` already enforces a token budget and compresses chunks.
51|- `ReActAgent` stores every user message, tool call, and assistant response as
52|  a `ContextChunk` — but only retrieves the last 5 via `get_recent_context()`.
53|- There is no summarization or sliding-window compression; old chunks are
54|  simply never re-fetched.
55|
56|**Production patterns:**
57|
58|1. **Sliding window with summarization.** Keep the last N turns verbatim;
59|   compress older turns into a running summary. Reduces token cost by 40–60%
60|   without meaningful quality loss.
61|2. **Priority-based retention.** System-critical information (user preferences,
62|   active task state) is never compressed; chit-chat and redundant
63|   confirmations are dropped first.
64|3. **Token budget allocation.** Reserve fixed portions: e.g., 50% system +
65|   tools, 30% conversation history, 20% retrieved long-term memory.
66|
67|### 2.2 Long-Term Memory (Persistent Memory)
68|
69|**Definition:** Information that survives session boundaries. Stored outside
70|the context window and retrieved on demand.
71|
72|**Characteristics:**
73|
74|| Property | Value |
75||---|---|
76|| Latency | 5–100 ms (retrieval) |
77|| Duration | Cross-session (weeks to indefinite) |
78|| Capacity | Unlimited (with retrieval limits) |
79|| Retrieval | Query-based — structured lookup + vector similarity |
80|| Failure mode | Retrieval precision failure, stale memories, unbounded growth |
81|
82|**Current state in AgentHarness:**
83|
84|- `ContextChunk` already has `embedding vector(1536)` and pgvector HNSW index.
85|- `ContextManager.search_by_embedding()` exists but is never called from the
86|  agent loop — `retrieved_chunks=[]` is hardcoded in `ReActAgent.run()`.
87|- There is no cross-session retrieval: `search_by_embedding()` filters by
88|  `session_id`, so memories from previous sessions are invisible.
89|
90|**Production patterns:**
91|
92|1. **Structured memory entries.** Store key-value pairs with metadata, not raw
93|   chat dumps. Each entry should have: `user_id`, `category` (preference,
94|   fact, decision, event), `importance` score, `created_at`, `accessed_at`.
95|2. **Vector search for semantic retrieval.** Embed the query, find top-k
96|   similar memories, inject into context.
97|3. **Hybrid retrieval.** Combine dense vector search with sparse BM25 keyword
98|   search and metadata filters (date range, category, user_id).
99|4. **Selective injection.** Never flood context — retrieve only what is
100|   relevant to the current task.
101|
102|### 2.3 The Handoff Between Layers
103|
104|The critical design decision is **what moves from short-term to long-term**.
105|A production system needs an explicit write path:
106|
107|```
108|Observation → Extraction → Dedup → Importance Scoring → Write to Long-Term
109|```
110|
111|Without this, long-term memory is either empty (nothing written) or a junkyard
112|(everything written).

116|## 3. Memory Consolidation
117|
118|### 3.1 What Is Consolidation?
119|
120|Consolidation is the process of transforming raw episodic traces (conversation
121|turns, tool calls, observations) into durable semantic memories (facts,
122|preferences, decisions). It is the agent equivalent of sleep-phase memory
123|consolidation in biological systems.
124|
125|### 3.2 When to Consolidate
126|
127|Three common triggers:
128|
129|| Trigger | Description | Cost |
130||---|---|---|
131|| **Synchronous** | After every turn, extract and store memories immediately | High latency per turn |
132|| **Asynchronous batch** | Queue observations; run consolidation every N turns or K seconds | Decoupled from inference |
133|| **End-of-session** | When a session ends, consolidate the entire conversation | One-time cost, but risks data loss if session crashes |
134|
135|**Recommendation for AgentHarness:** Start with asynchronous batch
136|consolidation (every 20 turns or on session archive). This keeps the hot path
137|fast while ensuring memories are persisted.
138|
139|### 3.3 What to Extract
140|
141|Not everything should be consolidated. A well-designed extraction step filters
142|on two dimensions:
143|
144|- **Novelty:** Is this meaningfully different from what we already know?
145|- **Utility:** Is this likely to be useful in future tasks?
146|
147|**Extract:**
148|- User preferences ("user prefers concise responses")
149|- Decisions ("chose PostgreSQL over MongoDB for the project")
150|- Facts ("user's account ID is 4782, subscription tier: Pro")
151|- Task outcomes ("deployment failed due to port conflict")
152|
153|**Do NOT extract:**
154|- Small talk and greetings
155|- Redundant confirmations ("ok", "thanks")
156|- Ephemeral state (weather readings, stock prices) unless the task is
157|  explicitly about historical time-series data
158|
159|### 3.4 Deduplication and Conflict Resolution
160|
161|Before writing a new memory, check for existing memories with similar
162|embeddings. If a match is found:
163|
164|- **Update** the existing memory if the new information is newer or more
165|  specific.
166|- **Merge** if both contain unique information.
167|- **Discard** if the new memory is redundant.
168|
169|Conflict resolution strategies:
170|- **Last-write-wins:** Simplest; works for most preference updates.
171|- **Confidence-weighted:** Each memory has a confidence score; higher
172|  confidence wins.
173|- **LLM-arbitrated:** Ask the LLM to resolve contradictions (expensive but
174|  most accurate).
175|
176|### 3.5 Implementation Sketch for AgentHarness
177|
178|```python
179|class MemoryConsolidator:
180|    """Consolidates raw context chunks into durable long-term memories."""
181|
182|    def __init__(
183|        self,
184|        llm_provider: LLMProvider,
185|        importance_scorer: ImportanceScorer,
186|        dedup_threshold: float = 0.85,
187|    ):
188|        self.llm = llm_provider
189|        self.scorer = importance_scorer
190|        self.dedup_threshold = dedup_threshold
191|
192|    async def consolidate_session(
193|        self,
194|        session_id: uuid.UUID,
195|        agent_id: str,
196|    ) -> list[MemoryEntry]:
197|        """Consolidate a session's context chunks into long-term memories."""
198|        chunks = await context_manager.get_chunks(session_id, limit=100)
199|        conversation = self._format_conversation(chunks)
200|
201|        # Step 1: Extract candidate memories via LLM
202|        candidates = await self._extract_memories(conversation)
203|
204|        # Step 2: Score importance
205|        for candidate in candidates:
206|            candidate.importance = self.scorer.score(candidate)
207|
208|        # Step 3: Deduplicate against existing memories
209|        new_memories = []
210|        for candidate in candidates:
211|            existing = await self._find_similar(candidate)
212|            if existing and self._similarity(candidate, existing) > self.dedup_threshold:
213|                await self._merge_or_update(existing, candidate)
214|            else:
215|                new_memories.append(candidate)
216|
217|        # Step 4: Write new memories
218|        for memory in new_memories:
219|            await self._write_memory(memory, agent_id)
220|
221|        return new_memories
222|```

226|## 4. Forgetting Curves
227|
228|### 4.1 The Ebbinghaus Forgetting Curve
229|
230|Human memory retention follows exponential decay: without reinforcement,
231|memories weaken rapidly in the first hours/days, then stabilize at a lower
232|level. The classic formula:
233|
234|```
235|R(t) = e^(-t/S)
236|```
237|
238|Where `R` is retention, `t` is time, and `S` is memory strength.
239|
240|### 4.2 Applying Decay to Agent Memory
241|
242|Each memory has a **retrieval strength** that decays over time but is
243|reinforced on access:
244|
245|```
246|strength(t) = base_strength × e^(-λ × Δt) + access_boost
247|```
248|
249|- `λ` (decay rate): Controls how fast memories fade. A half-life of 14 days
250|  is a reasonable default: `λ = ln(2) / 14 ≈ 0.05`.
251|- `access_boost`: Each time a memory is retrieved, its strength is boosted
252|  (simulating spaced repetition).
253|
254|### 4.3 Importance-Modulated Decay
255|
256|Not all memories should decay at the same rate. High-importance memories
257|(user preferences, critical decisions) should decay slowly or not at all.
258|Low-importance memories (one-off events, transient state) should decay
259|quickly.
260|
261|```
262|effective_decay = base_decay × (1 - importance)
263|```
264|
265|A memory with `importance = 0.9` decays at 10% of the base rate.
266|A memory with `importance = 0.1` decays at 90% of the base rate.
267|
268|### 4.4 Eviction Policies
269|
270|When memory storage reaches capacity:
271|
272|| Policy | Description | Best For |
273||---|---|---|
274|| **LRU** | Evict least recently accessed | General purpose |
275|| **LFU** | Evict least frequently accessed | Stable knowledge |
276|| **Importance-based** | Evict lowest importance score | Production agents |
277|| **TTL** | Evict after a time window | Ephemeral data |
278|
279|**Recommendation:** Use importance-based eviction as the primary policy,
280|with TTL as a safety net for low-importance memories.
281|
282|### 4.5 Implementation Sketch
283|
284|```python
285|class ForgettingModel:
286|    """Ebbinghaus-inspired decay with importance modulation."""
287|
288|    def __init__(self, half_life_days: float = 14.0):
289|        self.base_lambda = 0.693 / half_life_days  # ln(2) / half_life
290|
291|    def current_strength(self, memory: MemoryEntry) -> float:
292|        """Compute current retrieval strength of a memory."""
293|        days_since_access = (datetime.utcnow() - memory.accessed_at).days
294|        importance_factor = 1.0 - memory.importance
295|        effective_lambda = self.base_lambda * importance_factor
296|        decay = math.exp(-effective_lambda * days_since_access)
297|        return memory.base_strength * decay + memory.access_count * 0.1
298|
299|    def should_forget(self, memory: MemoryEntry, threshold: float = 0.05) -> bool:
300|        """Decide whether a memory should be evicted."""
301|        return self.current_strength(memory) < threshold
302|```

306|## 5. Importance Scoring
307|
308|### 5.1 Why Importance Matters
309|
310|Importance scoring determines:
311|- **What gets written** to long-term memory (write path)
312|- **What gets evicted** when storage is full (forgetting)
313|- **What gets retrieved** first (read path ranking)
314|
315|### 5.2 Multi-Factor Importance Model
316|
317|Research (arXiv 2606.12945, "Learning What to Remember") shows that a
318|multi-factor value model outperforms single-factor (recency or similarity)
319|policies. The proposed value function:
320|
321|```
322|V(m) = Σ wᵢ × fᵢ(m)
323|```
324|
325|Where `fᵢ` are interpretable factors and `wᵢ` are learned weights.
326|
327|**Candidate factors:**
328|
329|| Factor | Description | Weight (learned) |
330||---|---|---|
331|| **Reliability** | Is this from a trusted source? | 0.64 |
332|| **Emotional intensity** | Does this carry emotional weight? | 0.55 |
333|| **Self/user relevance** | Is this about the user or their goals? | 0.23 |
334|| **Goal relevance** | Is this relevant to the current task? | 0.00 (blind) |
335|| **Recency** | How recently was this created/accessed? | varies |
336|| **Frequency** | How often has this been accessed? | varies |
337|| **Task utility** | Does this help complete the current task? | varies |
338|
339|**Key insight from the research:** Goal relevance is correctly down-weighted
340|for the *forgetting* decision (because the future query is unknown at
341|consolidation time), but is the dominant factor for *retrieval* (where the
342|query is known).
343|
344|### 5.3 Practical Scoring for AgentHarness
345|
346|For the initial implementation, use a simpler heuristic model that can be
347|learned later:
348|
349|```python
350|class ImportanceScorer:
351|    """Heuristic importance scoring for memory entries."""
352|
353|    def score(self, memory: MemoryEntry) -> float:
354|        """Return importance score in [0, 1]."""
355|        scores = []
356|
357|        # Category-based base importance
358|        category_weights = {
359|            "preference": 0.9,
360|            "decision": 0.8,
361|            "fact": 0.7,
362|            "event": 0.5,
363|            "transient": 0.2,
364|        }
365|        scores.append(category_weights.get(memory.category, 0.5))
366|
367|        # User explicit importance (if user said "remember this")
368|        if memory.explicitly_important:
369|            scores.append(1.0)
370|
371|        # Recency boost (decays over 30 days)
372|        days_old = (datetime.utcnow() - memory.created_at).days
373|        recency_score = max(0, 1.0 - days_old / 30.0)
374|        scores.append(recency_score * 0.3)
375|
376|        # Access frequency boost
377|        freq_score = min(1.0, memory.access_count / 10.0)
378|        scores.append(freq_score * 0.2)
379|
380|        return min(1.0, max(0.0, sum(scores) / len(scores)))
381|```
382|
383|### 5.4 Learning the Weights
384|
385|The weights can be learned from downstream task performance:
386|
387|1. Log all memory decisions (what was stored, what was retrieved, what was
388|   forgotten).
389|2. Measure task success (did the agent produce the correct answer?).
390|3. Use a gradient-free optimizer (e.g., Bayesian optimization) to find
391|   weights that maximize task success.
392|
393|This is a future enhancement — start with hand-tuned weights.

397|## 6. Memory Retrieval
398|
399|### 6.1 The Retrieval Problem
400|
401|Given a user query, find the most relevant memories from long-term storage
402|and inject them into the context window. The challenge is doing this
403|precisely (no irrelevant memories) and efficiently (low latency).
404|
405|### 6.2 Retrieval Strategies
406|
407|| Strategy | Description | Best For |
408||---|---|---|
409|| **Dense vector search** | Embed query, find nearest neighbors | Semantic similarity |
410|| **Sparse keyword search** | BM25 / TF-IDF on memory content | Exact matches, IDs |
411|| **Hybrid search** | Combine dense + sparse | Production systems |
412|| **Metadata filter** | Filter by date, category, user | Structured queries |
413|| **Graph traversal** | Walk a knowledge graph from seed nodes | Multi-hop reasoning |
414|
415|### 6.3 Hybrid Retrieval Pipeline
416|
417|```
418|Query
419|  │
420|  ├──→ Dense embedding → Vector search → Top-K candidates
421|  │
422|  ├──→ Sparse keywords → BM25 search → Top-K candidates
423|  │
424|  └──→ Metadata filter → Filter by user_id, date, category
425|         │
426|         ▼
427|   Merge & deduplicate
428|         │
429|         ▼
430|   Re-rank (cross-encoder or LLM)
431|         │
432|         ▼
433|   Inject top-N into context
434|```
435|
436|### 6.4 Query Formulation
437|
438|The agent's immediate input is often a poor retrieval query. A user asking
439|"Why did that crash?" needs the agent to retrieve the crash log from two
440|sessions ago, not the most semantically similar sentence.
441|
442|**Strategies:**
443|- **LLM-reformulated queries:** Ask the LLM to generate a better retrieval
444|  query from the user's input.
445|- **Multi-query fan-out:** Generate multiple retrieval queries and merge
446|  results.
447|- **Subgoal-based retrieval:** Use the current task subgoal as an
448|  additional retrieval signal.
449|
450|### 6.5 Re-ranking
451|
452|After initial retrieval, pass candidates through a cross-encoder or a
453|small LLM to score relevance more precisely. This is especially important
454|when the candidate set is large (>20).
455|
456|### 6.6 Implementation Sketch for AgentHarness
457|
458|```python
459|class MemoryRetriever:
460|    """Hybrid retrieval for long-term memory."""
461|
462|    def __init__(
463|        self,
464|        embedding_model: EmbeddingModel,
465|        top_k: int = 5,
466|        rerank: bool = True,
467|    ):
468|        self.embedding_model = embedding_model
469|        self.top_k = top_k
470|        self.rerank = rerank
471|
472|    async def retrieve(
473|        self,
474|        query: str,
475|        user_id: str,
476|        category: str | None = None,
477|        date_range: tuple[datetime, datetime] | None = None,
478|    ) -> list[RetrievedMemory]:
479|        """Retrieve relevant memories for a query."""
480|        # Step 1: Dense vector search
481|        query_embedding = await self.embedding_model.embed(query)
482|        dense_results = await self._vector_search(
483|            query_embedding, user_id, category, date_range
484|        )
485|
486|        # Step 2: Sparse keyword search
487|        sparse_results = await self._keyword_search(
488|            query, user_id, category, date_range
489|        )
490|
491|        # Step 3: Merge and deduplicate
492|        candidates = self._merge_results(dense_results, sparse_results)
493|
494|        # Step 4: Re-rank
495|        if self.rerank:
496|            candidates = await self._rerank(query, candidates)
497|
498|        return candidates[: self.top_k]
499|```
500|
501|### 6.7 Integration with AgentHarness
502|
503|The retrieval should be integrated into `ReActAgent.run()`:
504|
505|```python
506|# In ReActAgent.run(), replace:
507|retrieved_chunks=[],
508|
509|# With:
510|retrieved_memories = await memory_retriever.retrieve(
511|    query=user_message,
512|    user_id=session.agent_id,  # or a real user_id
513|)
514|retrieved_chunks = [
515|    (ContextChunk(
516|        id=m.id,
517|        session_id=session_id,
518|        agent_id=self.agent_id,
519|        chunk_type="memory",
520|        payload={"content": m.content, "importance": m.importance},
521|        token_count=len(m.content) // 4,
522|    ), m.score)
523|    for m in retrieved_memories
524|]
525|```

532|

545|│  └─────────────┘  └──────────────┘  └────────────┘ │

548|│  └──────────────────────────────────────────────┘   │

550|                       ▲
551|                       │ consolidate
552|┌──────────────────────┴──────────────────────────────┐

600|### 7.4 Integration Points
601|
602|1. **`ReActAgent.run()`:** Call `MemoryRetriever.retrieve()` before prompt
603|   assembly; pass results as `retrieved_chunks`.
604|2. **`ReActAgent` (post-run):** Call `MemoryConsolidator.consolidate_session()`
605|   asynchronously after the agent loop completes.
606|3. **`SessionManager.archive()`:** Trigger consolidation before marking
607|   session as archived.
608|4. **Background task:** Periodic forgetting pass (evict low-strength memories).

612|## 8. Production Lessons
613|
614|### 8.1 Anti-Patterns to Avoid
615|
616|| Anti-Pattern | Why It Fails | Fix |
617||---|---|---|
618|| **Context window maximalism** | Filling the full context window causes cost explosion and "lost in the middle" degradation | Use retrieval, not stuffing |
619|| **No decay policy** | Storing every interaction without decay leads to context drift | Implement Ebbinghaus decay from day one |
620|| **Single embedding model** | General-purpose embeddings fail on domain-specific content | Fine-tune or use domain-specific models |
621|| **No namespace isolation** | Sharing one vector index across users creates data leakage | Always partition by `user_id` |
622|| **Storing raw chat dumps** | Unstructured data degrades retrieval precision | Extract structured facts before storing |
623|| **No deduplication** | Redundant memories dilute retrieval results | Always dedup before writing |
624|
625|### 8.2 Key Metrics to Track
626|
627|| Metric | Target | Why |
628||---|---|---|
629|| **Retrieval precision@5** | > 0.8 | Are we retrieving the right memories? |
630|| **Retrieval latency (p99)** | < 100 ms | Is retrieval fast enough? |
631|| **Memory growth rate** | < 100 memories/day/user | Is the store growing unboundedly? |
632|| **Forgetting accuracy** | > 0.9 | Are we forgetting the right things? |
633|| **Token cost per turn** | < 4000 tokens | Is the context window being used efficiently? |
634|
635|### 8.3 Existing Solutions
636|
637|| Solution | Strength | Best For |
