7|## 1. Context Compression (`/compress` / `/compact`)
8|
9|### Architecture: Dual Compression System
10|
11|Hermes uses **two independent compression layers** that operate at different thresholds:
12|
13|```
14|                     ┌──────────────────────────┐
15|  Incoming message   │   Gateway Session Hygiene │  Fires at 85% of context
16|  ─────────────────► │   (pre-agent, rough est.) │  Safety net for large sessions
17|                     └─────────────┬────────────┘
18|                                   │
19|                                   ▼
20|                     ┌──────────────────────────┐
21|                     │   Agent ContextCompressor │  Fires at 50% of context (default)
22|                     │   (in-loop, real tokens)  │  Normal context management
23|                     └──────────────────────────┘
24|```
25|
26|#### Layer 1: Gateway Session Hygiene (85% threshold)
27|- **Location**: `gateway/run_turn.py`
28|- **Purpose**: Safety net for sessions that grow between turns (e.g., overnight Telegram/Discord accumulation)
29|- **Token source**: Prefers API-reported tokens from last turn → usage anchor on session row → rough character-based estimate
30|- **Fires**: Only when `len(history) >= 4` and compression is enabled
31|- **Why 85%?**: Intentionally higher than the agent compressor. Setting it at 50% caused premature compression on every turn in long gateway sessions.
32|
33|#### Layer 2: Agent ContextCompressor (50% threshold, configurable)
34|- **Location**: `agent/context_compressor.py`
35|- **Purpose**: Primary compression system, runs inside the agent's tool loop with accurate API-reported token counts
36|- **Token accounting**: Uses "provider anchors" — the provider's last prompt/completion token counts plus a rough estimate of only the messages appended since that response. The anchor is persisted on the session row so a fresh process (`--resume`) restores it.
37|- **Fallback**: Without an anchor (first request, rewind/edit-resend), a whole-context rough estimate over threshold **waits one request** for provider evidence before compressing.
38|
39|### The 4-Phase Compression Algorithm
40|
41|The `ContextCompressor.compress()` method follows this sequence:
42|
43|#### Phase 1: Prune Old Tool Results (cheap, no LLM call)
44|- Old tool results (>200 chars) outside the protected tail are replaced with `[Old tool output cleared to save context space]`
45|- A tool round the model has not answered yet keeps its text results verbatim and image results intact in the tail
46|- A tool round exceeding 20% of the input budget can be summarized, with older images retired
47|
48|#### Phase 2: Determine Boundaries
49|```
50|┌─────────────────────────────────────────────────────────────┐
51|│  Message list                                               │
52|│                                                             │
53|│  [0..2]  ← protect_first_n (system + first exchange)        │
54|│  [3..N]  ← middle turns → SUMMARIZED                        │
55|│  [N..end] ← tail (by token budget OR protect_last_n)        │
56|│                                                             │
57|└─────────────────────────────────────────────────────────────┘
58|```
59|- Tail protection is **token-budget based**: walks backward from the end, accumulating tokens until budget is exhausted
60|- Budget capped at 20% of context window on every model
61|- `protect_last_n` (default 20) is a minimum only up to a small count floor (8 rows)
62|- `min_tail_user_messages` (default 1) guarantees at least 1 real user message survives
63|- Boundaries aligned to avoid splitting tool_call/tool_result groups
64|
65|#### Phase 3: Generate Structured Summary
66|- The middle turns are sent to an **auxiliary LLM** (can be a smaller/cheaper model) with a structured template:
67|
68|```text
69|## Goal
70|[What the user is trying to accomplish]
71|
72|## Constraints & Preferences
73|[User preferences, coding style, constraints, important decisions]
74|
75|## Progress
76|### Done
77|[Completed work — specific file paths, commands run, results]
78|### In Progress
79|[Work currently underway]
80|### Blocked
81|[Any blockers or issues encountered]
82|
83|## Key Decisions
84|[Important technical decisions and why]
85|
86|## Relevant Files
87|[Files read, modified, or created — with brief note on each]
88|
89|## Next Steps
90|[What needs to happen next]
91|
92|## Critical Context
93|[Specific values, error messages, configuration details]
94|```
95|
96|- Summary budget: `content_tokens × 0.20` (min 2,000, max `min(context_length × 0.05, 12,000)`)
97|- The summary model's context window must be ≥ the main model's, or the summary silently fails
98|
99|#### Phase 4: Assemble Compressed Messages
100|1. Head messages (with a note appended to system prompt on first compression)
101|2. Summary message (role chosen to avoid consecutive same-role violations)
102|3. Tail messages (unmodified)
103|- Orphaned tool_call/tool_result pairs cleaned up by `_sanitize_tool_pairs()`
104|
105|### Iterative Re-compression
106|On subsequent compressions, the previous summary is passed to the LLM with instructions to **update** it rather than summarize from scratch. This preserves information across multiple compactions — items move from "In Progress" to "Done", new progress is added, obsolete information is removed.
107|
108|### Tail Modes
109|
110|| Mode | Behavior |
111||------|----------|
112|| `lean` (default) | Clamped tail of 2.5% × context window (10K floor, 25K cap). Carries continuity via: detailed identifier-preserving session log, mechanically extracted anchor index (PR numbers, SHAs, paths, error strings — regex, never paraphrased), every real user message quoted verbatim (newest-first budget), and a `session_search` recovery pointer. Old tool results demoted to one-line stubs with recovery pointer. |
113|| `legacy` | Keeps a `target_ratio`-sized verbatim tail (~100K+ tokens on big-window models) |
114|
115|### In-Place Compaction (default: `in_place: true`)
116|- Compaction **rewrites the live message list on the same session id**
117|- Pre-compaction turns are soft-archived under the same id (`active=0, compacted=1`)
118|- Still searchable via `session_search` and recoverable, never deleted
119|- No `parent_session_id` chain, no `name #N` renumbering
120|- One conversation keeps one durable id for its whole life
121|
122|### Failure Handling
123|- **Failure cooldown**: Escalating 60s → 300s → 900s, persisted in `state.db`. While armed, ordinary threshold-triggered compaction is deferred.
124|- **Manual `/compress`** (`force=True`): Clears the cooldown and retries.
125|- **Repeated stall → deterministic fallback**: After 2 consecutive stalls, commits a static fallback summary through the ordinary pipeline.
126|- **Provider overload → abort**: Preserves transcript unchanged. After 3 consecutive overload aborts, commits deterministic fallback.
127|- **Provider-proven overflow**: When provider rejects with context-length error, ignores cooldown for one bounded attempt.
128|
129|### Configuration
130|
131|```yaml
132|compression:
133|  enabled: true
134|  threshold: 0.50            # Fraction of context window (default: 0.50)
135|  threshold_tokens: null     # Optional absolute cap on trigger
136|  model_thresholds: {}       # Per-model overrides (substring match, longest key wins)
137|  target_ratio: 0.20         # Tail protection token budget (legacy mode)
138|  tail_mode: lean            # lean | legacy
139|  protect_last_n: 20         # Minimum protected tail messages
140|  min_tail_user_messages: 1  # Real user messages guaranteed in tail
141|  protect_first_n: 3         # Hardcoded: system prompt + first exchange
142|  idle_compact_after_seconds: 0  # Opt-in idle compaction
143|  in_place: true             # Compact on same session id
144|
145|auxiliary:
146|  compression:
147|    model: null              # Override model for summaries
148|    provider: auto           # Provider for summaries
149|```
150|
151|### Per-Model Threshold Overrides
152|```yaml
153|compression:
154|  model_thresholds:
155|    "glm-5.2": 0.40
156|    "claude-sonnet": 0.35
157|    "openai-codex:astra": 0.85   # only on Codex OAuth route
158|```
159|- Keys are substring-matched against model name; longest match wins
160|- Provider-scoped keys (`<provider>:<substring>`) only match on that route
161|- Small-context floor (0.75 for <512K windows) applies on top (raise-only)
162|
163|### Prompt Caching Integration
164|- Anthropic Claude models get automatic prompt caching via `cache_control`
165|- TTL: `5m` (default) or `1h` for human-paced sources; `auto` resolves per session
166|- Cache-aware design: system prompt + first 3 messages are cached; rolling 3-message window re-establishes caching within 1-2 turns after compaction
167|- Model identity is part of the cache key — mid-conversation model changes get zero cache hits
168|
169|### Context Pressure Warnings
170|- **Removed** — intermediate pressure warnings caused models to "give up" prematurely on complex tasks
171|- Compression fires at threshold with no prior warning step

175|## 2. Token Usage Tracking (`/usage`)
176|
177|### How It Works
178|
179|1. **Per-API-call accumulation** (`agent/conversation_loop.py`): After every API call, the response's usage object is normalized via `normalize_usage()` from `agent/usage_pricing.py` into a `CanonicalUsage` dataclass:
180|   - `input_tokens` — raw input (excludes cache)
181|   - `output_tokens` — generated tokens
182|   - `cache_read_tokens` — cache hits
183|   - `cache_write_tokens` — cache writes
184|   - `reasoning_tokens` — thinking/reasoning tokens
185|
186|2. **Session counters** on the AIAgent instance:
187|   ```python
188|   agent.session_input_tokens += canonical_usage.input_tokens
189|   agent.session_output_tokens += canonical_usage.output_tokens
190|   agent.session_cache_read_tokens += canonical_usage.cache_read_tokens
191|   agent.session_cache_write_tokens += canonical_usage.cache_write_tokens
192|   agent.session_reasoning_tokens += canonical_usage.reasoning_tokens
193|   agent.session_total_tokens += total_tokens
194|   agent.session_api_calls += 1
195|   agent.session_estimated_cost_usd += cost
196|   ```
197|
198|3. **Persisted to SQLite** via `SessionDB.update_token_counts()` (`hermes_state.py`)
199|
200|### The `/usage` Slash Command
201|- Reads the live agent's session counters (mid-turn) or cached agent (between turns)
202|- Calls `fetch_account_usage()` from `agent/account_usage.py` for provider-level rate limits
203|- Calls `estimate_usage_cost()` from `agent/usage_pricing.py` for cost estimates
204|- **Shows**: model, input tokens, cache read/write, output tokens, total, API calls, cost, context window %
205|- Gateway handler: `gateway/run.py` line 13194 (`_handle_usage_command`)
206|- CLI: `cli.py` → `process_command`
207|
208|### Programmatic Access
209|```python
210|agent = AIAgent(...)
211|agent.chat("hello")
212|print(f"In: {agent.session_input_tokens}, Out: {agent.session_output_tokens}")
213|print(f"Total: {agent.session_total_tokens}, API calls: {agent.session_api_calls}")
214|print(f"Cost: ${agent.session_estimated_cost_usd:.4f}")
215|```
216|
217|### One-Shot Usage Report
218|```bash
219|hermes -z "..." --usage-file /path/report.json
220|```
221|Writes a machine-readable JSON usage report after the run: `estimated_cost_usd`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens`, `total_tokens`, `api_calls`, `model`, `provider`, `session_id`, `service_tier`, `completed`/`failed` flags.

225|## 3. Usage Analytics (`/insights`)
226|
227|### The `InsightsEngine` (`agent/insights.py`)
228|
229|Inspired by Claude Code's `/insights` command, adapted for Hermes Agent's multi-platform architecture.
230|
231|```python
232|from agent.insights import InsightsEngine
233|engine = InsightsEngine(db)
234|report = engine.generate(days=30)
235|print(engine.format_terminal(report))
236|```
237|
238|### What It Analyzes
239|- **Token consumption** across sessions
240|- **Cost estimates** (USD) using `estimate_usage_cost()` from `agent/usage_pricing.py`
241|- **Tool usage patterns** — which tools are used most
242|- **Activity trends** — usage over time
243|- **Model/platform breakdowns** — which models and platforms are used
244|- **Session metrics** — duration, message counts, etc.
245|
246|### CLI Command
247|```bash
248|hermes insights [--days N] [--source platform]
249|```
250|- `--days N`: Analyze last N days (default 30)
251|- `--source platform`: Filter by platform (cli, telegram, discord, etc.)
252|- Works offline — derived from local session history in SQLite
253|
254|### In-Session Slash Command
255|```
256|/insights [days]
257|```
258|Shows usage analytics for the specified period (default 30 days).
259|
260|### Data Source
261|All insights come from the SQLite `state.db` — session metadata, token counts, and message history. No external API calls needed.

265|## 4. User Modeling (USER.md)
266|
267|### Two-File Memory System
268|
269|| File | Purpose | Char Limit | Who Writes |
270||------|---------|------------|------------|
271|| **MEMORY.md** | Agent's personal notes — environment facts, conventions, things learned | 2,200 chars (~800 tokens) | Agent via `memory` tool |
272|| **USER.md** | User profile — preferences, communication style, expectations | 1,375 chars (~500 tokens) | Agent via `memory` tool |
273|
274|Both stored in `~/.hermes/memories/` and injected into the system prompt as a **frozen snapshot** at session start.
275|
276|### How USER.md Is Built
277|
278|The agent **automatically** builds the user profile — you don't need to ask. It saves when it learns:
279|
280|- **User preferences**: "I prefer TypeScript over JavaScript" → save to `user`
281|- **Communication style**: "Don't use sudo for Docker commands, user is in docker group" → save to `memory`
282|- **Corrections**: "Project uses tabs, 120-char line width" → save to `memory`
283|- **Name, role, timezone** → save to `user`
284|- **Pet peeves and things to avoid** → save to `user`
285|- **Workflow habits** → save to `user`
286|- **Technical skill level** → save to `user`
287|
288|### Memory Tool Actions
289|
290|- **add** — Add a new memory entry
291|- **replace** — Replace an existing entry (uses substring matching via `old_text`)
292|- **remove** — Remove an entry (uses substring matching via `old_text`)
293|- No `read` action — memory content is automatically injected into the system prompt
294|
295|### Substring Matching
296|```python
297|memory(action="replace", target="memory",
298|       old_text="dark mode",
299|       content="User prefers light mode in VS Code, dark mode in terminal")
300|```
301|- `old_text` only locates the entry; `replace` overwrites the **whole matched entry**
302|- If substring matches multiple entries, returns error asking for more specific match
303|
304|### Frozen Snapshot Pattern
305|- System prompt injection is captured once at session start and never changes mid-session
306|- When agent adds/removes memory entries, changes persist to disk immediately but won't appear in system prompt until next session
307|- **Why**: Preserves LLM's prefix cache for performance
308|- Tool responses always show live state
309|
310|### Capacity Management
311|- When a write would exceed the limit, the tool returns an error with current entries and usage
312|- Agent consolidates/removes entries in the same turn before retrying
313|- Best practice: When memory is above 80% capacity, consolidate before adding
314|
315|### Duplicate Prevention
316|- Automatically rejects exact duplicate entries
317|
318|### Security Scanning
319|- Memory entries scanned for injection and exfiltration patterns before being accepted
320|- Content matching threat patterns (prompt injection, credential exfiltration, SSH backdoors) or containing invisible Unicode characters is blocked
321|
322|### Write Approval Gate
323|```yaml
324|memory:
325|  write_approval: false     # false = write freely (default) | true = require approval
326|```
327|- When `true`, writes are staged for review with `/memory pending` and `/memory approve all`
328|- Applies to both foreground turns and background self-improvement review
329|
330|### What to Save vs Skip
331|
332|**Save**: User preferences, environment facts, corrections, conventions, completed work, explicit requests
333|**Skip**: Trivial/obvious info, easily re-discovered facts, raw data dumps, session-specific ephemera, information already in context files

337|## 5. Cross-Session Recall (`session_search`)
338|
339|### Architecture
340|
341|All sessions stored in SQLite (`~/.hermes/state.db`) with **FTS5 full-text search**:
342|
343|```
344|~/.hermes/state.db (SQLite, WAL mode)
345|├── sessions              — Session metadata, token counts, billing
346|├── messages              — Full message history per session
347|├── messages_fts          — FTS5 virtual table (content + tool_name + tool_calls)
348|├── messages_fts_trigram  — FTS5 virtual table with trigram tokenizer (CJK / substring search)
349|├── state_meta            — Key/value metadata table
350|└── schema_version        — Single-row table tracking migration state
351|```
352|
353|### The `session_search` Tool
354|
355|**No LLM calls** — returns actual messages from the DB, byte-for-byte. No summarization, no truncation.
356|
357|#### Three Calling Shapes
358|
359|**1. Discovery** — pass `query`:
360|```python
361|session_search(query="auth refactor", limit=3)
362|```
363|- Runs FTS5, dedupes hits by session lineage, returns top N sessions
364|- Adaptive detail: highest-ranked result gets full context window + bookends; lower-ranked stay compact
365|- Each result carries: `session_id`, `title`, `when`, `source`, `snippet`, `detail`, `bookend_start`/`bookend_end` (first/last 3 user+assistant messages), `messages` (±5 around match), `match_message_id`, `messages_before`, `messages_after`
366|- **Wall time**: ~20ms (vs ~90s for old LLM-summarization approach)
367|
368|**2. Scroll** — pass `session_id` + `around_message_id`:
369|```python
370|session_search(session_id="20260510_174648_805cc2", around_message_id=590803, window=10)
371|```
372|- Returns ±`window` messages centered on anchor
373|- No FTS5, no bookends — just the slice
374|- Scroll forward: pass `messages[-1].id` back as `around_message_id`
375|- Scroll backward: pass `messages[0].id` back as `around_message_id`
376|- **Wall time**: 1–2ms per scroll call
377|
378|**3. Read** — pass `session_id` without anchor:
379|```python
380|session_search(session_id="20260510_174648_805cc2")
381|```
382|- Returns whole session, or bounded head/tail view for large sessions
383|- Also resolves `@session:/` links
384|
385|**4. Browse** — no args:
386|- Returns recent sessions chronologically (titles, previews, timestamps)
387|- Useful when user asks "what was I working on" without naming a topic
388|
389|### FTS5 Query Syntax
390|- Simple keywords: `docker deployment` (implicit AND)
391|- Phrases: `"exact phrase"`
392|- Boolean: `docker OR kubernetes NOT java`
393|- Prefix: `deploy*`
394|
395|### Optional Parameters
396|- `sort` — `newest` or `oldest`, on top of FTS5 ranking
397|- `detail` — `adaptive` (default) or `full`
398|- `role_filter` — comma-separated roles (default: `user,assistant`)
399|
400|### When It's Used
401|The agent is prompted to use session search automatically:
402|> "When the user references something from a past conversation or you suspect relevant prior context exists, use session_search to recall it before asking them to repeat themselves."
403|
404|Typical triggers: "we did this before", "remember when", "last time", "as I mentioned"
405|
406|### Session Search vs Memory
407|
408|| Feature | Persistent Memory | Session Search |
409||---------|------------------|----------------|
410|| **Capacity** | ~1,300 tokens total | Unlimited (all sessions) |
411|| **Speed** | Instant (in system prompt) | ~20ms FTS5 query, ~1ms scroll |
412|| **Cost** | Token cost in every prompt | Free — no LLM calls |
413|| **Use case** | Key facts always available | Finding specific past conversations |
414|| **Management** | Manually curated by agent | Automatic — all sessions stored |
415|| **Token cost** | Fixed per session (~1,300 tokens) | On-demand (searched when needed) |
416|
417|### In-Place Compaction + Session Search
418|- Archived (compacted) content on the current session is discoverable via `session_search`
419|- Non-compacted (active) content on the current session is filtered out of results
420|- Compaction handoff summaries are excluded from bookends
421|
422|### Auto-Prune
423|- Ended sessions inactive for `sessions.retention_days` (default 90) are removed at startup
424|- Active sessions are never touched
425|- `hermes sessions prune` for one-off cleanup
426|- `hermes sessions optimize` merges FTS5 index segments and VACUUMs

430|## 6. External Memory Providers
431|
432|For deeper, persistent memory beyond MEMORY.md and USER.md, Hermes ships with 7 external provider plugins:
433|
434|| Provider | Best For |
435||----------|----------|
436|| **Honcho** | AI-native cross-session user modeling with dialectic reasoning, semantic search, persistent conclusions |
437|| **OpenViking** | Knowledge graphs, semantic search |
438|| **Mem0** | Automatic fact extraction, user modeling |
439|| **Holographic** | Holographic memory |
440|| **RetainDB** | RetainDB memory |
441|| **ByteRover** | ByteRover memory |
442|| **Supermemory** | Supermemory |
443|
444|External providers run **alongside** built-in memory (never replacing it) and add capabilities like knowledge graphs, semantic search, automatic fact extraction, and cross-session user modeling.
445|
446|### Honcho (Most Relevant for User Modeling)
447|- **Two-layer context injection**: base layer (session summary + representation + peer card, refreshed on `contextCadence`) + dialectic supplement (LLM reasoning, refreshed on `dialecticCadence`)
448|- **Three orthogonal config knobs**: `contextCadence`, `dialecticCadence`, `dialecticDepth`
449|- **Tools**: `honcho_profile`, `honcho_search`, `honcho_context`, `honcho_reasoning`, `honcho_conclude`
450|- **Multi-agent support**: Each profile gets a dedicated AI peer while sharing the same user workspace

454|## 7. Key Takeaways for AgentHarness
455|
456|### Context Compression
457|- **Dual-layer approach**: Gateway hygiene (85%) as safety net + agent compressor (50%) as primary
458|- **4-phase algorithm**: Prune tool results → determine boundaries → structured summary → assemble
459|- **Iterative re-compression**: Previous summary is updated, not regenerated
460|- **In-place compaction**: Same session id, soft-archived content still searchable
461|- **Provider anchors**: Persisted token counts survive restarts
462|- **Failure cooldown**: Escalating backoff prevents thrashing
463|- **Pluggable engine**: `context.engine` config allows alternative implementations
464|
465|### Session Search
466|- **FTS5 full-text search** across all sessions — no LLM calls, no cost
467|- **Three shapes**: Discovery (query), Scroll (anchored window), Read (full session)
468|- **Bookend pattern**: First/last 3 messages reconstruct goal → match → resolution
469|- **~20ms discovery, ~1ms scroll** — fast enough for real-time use
470|- **Trigram tokenizer** for CJK/substring search
471|
472|### User Modeling
473|- **Two-file system**: MEMORY.md (agent notes) + USER.md (user profile)
474|- **Strict char limits**: 2,200 + 1,375 chars keep system prompts bounded
475|- **Frozen snapshot**: Injected at session start, never changes mid-session (preserves prefix cache)
476|- **Automatic**: Agent saves proactively when it learns preferences/corrections
477|- **Security scanning**: Injection/exfiltration patterns blocked
478|- **Write approval gate**: Optional review before persistence
479|
480|### Usage Tracking
481|- **CanonicalUsage dataclass**: Normalized across providers
482|- **Per-session counters**: Input, output, cache read/write, reasoning tokens, cost
483|- **Persisted to SQLite**: Survives restarts
484|- **Provider-level rate limits**: Via `fetch_account_usage()`
485|
486|### Analytics
487|- **InsightsEngine**: Token consumption, cost estimates, tool usage, activity trends, model/platform breakdowns
488|- **Offline**: All from local SQLite, no external API calls
489|- **CLI + slash command**: `hermes insights` and `/insights [days]`
490|
491|### Cross-Session Recall
492|- **session_search tool**: FTS5-based, no LLM, returns actual messages
493|- **Automatic triggering**: Agent prompted to search when user references past conversations
494|- **Recovery pointer in summaries**: Compressed content includes `session_search` pointer for re-access
495|- **External providers**: Honcho, Mem0, etc. for semantic search and user modeling beyond keyword search
