# UI and HTTP event protocol

The source of truth is `machina/protocol/events.json`, version **2**. Python validates
canonical emissions. `ui/src/events.ts` is generated by
`python -c "from pathlib import Path; from machina.protocol import typescript_source; Path('ui/src/events.ts').write_text(typescript_source(), encoding='utf-8')"`.
Conformance tests check the generated file byte for byte.

Gateway notifications use JSON-RPC 2.0: method `event`, with the event in `params`.
HTTP uses SSE: each `data:` frame contains the same event object. `[DONE]` closes a
normally retired HTTP stream; it is not a success verdict.
Every v2 event requires `protocolVersion: 2`, `type`, `sessionId`, and `turnId`.
Undeclared top-level fields and invalid field types are rejected. Object payloads
(`args`, `fileDiff`, approval summaries) carry their operation-specific data.
These data are transport payloads, never log or metric fields.

## Negotiation and migration

The TUI sends `protocolVersion: 2` with `initialize`; its response reports the
selected version. HTTP prompt/chat and approval-resume bodies accept
`protocolVersion: 2`; responses report the negotiated version in a header.
The current server emits the legacy spelling `X-AH-Protocol-Version: 2`;
`X-Machina-Protocol-Version` is the canonical forward name. Clients must treat
the two spellings as aliases for the same version value (the value, not the
prefix, is normative).
For compatibility, omission selects version 1. An unsupported version is rejected.
Version 1 gateway approval names are `permission.required` and
`permission.resolved`; the TUI accepts them during migration. Version 1 HTTP
retains `text/content`, `tool_call/tool`, `tool_result/tool`, `token_usage`, and
`done/content`, and the earlier nested `needs_approval/proposal` shape.
Operational start, loss, pending-cleanup and resume frames retain their existing
names. This compatibility path is explicit; canonical version 2 is shared.

## Approval and continuation

The durable proposal binds session, originating turn, agent, tool, argv, shell,
cwd, mode, backend, targets, capabilities, destinations, timeout, and content
identity. A human resolves the request using `approvals.resolve` (gateway) or
`POST /api/v1/approvals/{requestId}/resolve` (HTTP). Decision and execution are
separate atomic transitions. Agent principals cannot resolve approvals.
Gateway waits keep renewing ownership and exclude human wait from compute time.
HTTP pauses release the originating turn; `POST /api/v1/approvals/{requestId}/resume`
takes `sessionId`, originating `turnId`, exact `toolArgs`, and `protocolVersion`.
It acquires fresh fenced ownership and revalidates every material field through
the same agent/broker/tool pipeline. Changed actions require fresh approval;
denied, expired, cancelled, claimed or completed actions cannot be replayed.
HTTP continuation executes the reviewed tool once; further conversation is a new
prompt. Decision responses include `approval.resolved` and a continuation route.

## Terminal and disconnect semantics

Errors, loss and cleanup-pending never prove retirement. Gateway sends one
`message.complete` only after actual cleanup and claim release. HTTP buffers its
terminal event until cleanup/release. Resistant HTTP execution reports pending
cleanup and closes the response without a terminal completion or `[DONE]`; the
server retains ownership and renews until retirement. A disconnected consumer
receives no fabricated terminal event. Cancellation cannot guarantee termination
of arbitrary asyncio code, plugins, providers or external effects.

## RPC methods

Gateway requests use a monotonically increasing client id and object `params`.
Responses contain exactly one of `result` or `error` (`code`, sanitized `message`).
Methods are registered in `machina/gateway/server.py` and `machina/gateway/features/__init__.py`.
Mutating session operations require fenced mutation ownership; reads remain
available during turns. HTTP also exposes these authenticated methods through
`POST /api/v1/rpc`. The API OpenAPI document declares REST request/response shapes.
Application errors: 1001 database unavailable, 1002 session/not found, 1003 turn in
progress, 1004 operation failed, 1005 unauthorized. JSON-RPC standard errors apply
to malformed, missing or unknown methods/parameters.
# Personality growth

`growth.get {sessionId}` returns `{growth: {agent_id, notes, policy, interactions, feedback_count}, episodes: [...], rsi: {...}}`. Episodes include `id`, `session_id`, `action`, `completed`, `reward` and `created_at`. RSI status includes `enabled`, `revision`, `observations`, `automatic_observations`, `human_ratings`, bounded `skill_weights` and `tool_weights`, `trial: {revision, ratings, required: 3} | null`, and up to 50 history entries `{revision, reason, status, created_at}`. It does not expose revision snapshots or raw execution data. Operational/human counts can overlap; each episode contributes once, with human reward overriding its proxy.

`growth.teach {sessionId, kind, key, content}` saves a bounded preference/style/lesson; `growth.forget {sessionId, key}` removes a `kind:key` note. `growth.feedback {sessionId, episodeId, reward}` accepts a finite reward in [-1, 1] once for a completed decision in that session. `growth.installPolicy {sessionId, policy}` validates and installs six-action offline JSON weights with a safe live retrieval/noop mask. `growth.rollback {sessionId, revision}` accepts a nonnegative integer, including original baseline 0, and returns `{restored: boolean}`. A successful restore creates a fresh monotonic revision containing the chosen notes and policy; history remains bounded and immutable. Missing/pruned/foreign revisions return false; malformed revisions are invalid parameters.

Teaching, feedback and installation reject requests while memory or personality growth is disabled. Inspection, forgetting and rollback remain available. Disabling only `rsi_enabled` stops automatic evidence and adaptation; human management still protects existing revision history. These methods use the existing gateway token and derive the owning agent from the session. They also use the existing authenticated HTTP `POST /rpc` dispatch; callers cannot select a different owner via extra parameters.

## MCP management and native tool calls (2026-10-12)

This supersedes the earlier read-only phase limitation. Authenticated human
management methods now include `mcp.configure {config}`, `mcp.remove {id}`,
`mcp.preview {id,sessionId}`, `mcp.connect {id,sessionId,digest}`,
`mcp.disconnect {id}` and `mcp.tools {id}`. Configure saves validated,
reference-only installation-local configuration and never launches. Preview
returns the exact proposal/digest; connect consumes the human's confirmed
preview through the broker and rejects changed identities. Connect/disconnect
return `{server}`; configure returns `{server}`; removal returns `{removed}`;
tools returns `{tools,truncated}`. Listing/status remain no-launch reads.

No raw `mcp.call` RPC bypass exists. Native `mcp_list`, `mcp_describe` and
`mcp_call` use the agent pipeline and inherited tool restrictions. `tool.complete`
adds optional `outcome: "outcome_unknown"` for a dispatched call without a known
terminal result. Missing outcome preserves legacy behavior; unknown never renders
as success.

## MCP OAuth (2026-10-15)

Streamable-HTTP OAuth (authorization code + S256 PKCE, loopback callback,
dynamic client registration when advertised) is implemented and exposed as
authenticated human control-plane methods — never agent tools and never a raw
`mcp.call` bypass. All require a connector `id` and the caller's `sessionId`
(where accepted); one session cannot operate another session's preview/operation.
Unknown parameters are rejected. See [docs/MCP_OAUTH.md](../docs/MCP_OAUTH.md).

| Method | Params | Result |
|---|---|---|
| `mcp.oauth.preview` | `{id, sessionId, issuer?}` | `{previewId, digest, expiresAt, review: {connectorId, revision, endpoint, resource, issuer, requestedScopes, registrationMode, endpoints, redirectUri}, requiredScopes?, authChallenge?}`; or `{issuers: [...]}` when discovery needs an explicit issuer choice. Launch-free: no registration, no browser, no token request. |
| `mcp.oauth.start` | `{id, sessionId, previewId, digest}` | `{operation: {operationId, connectorId, state, expiresAt, reasonCode?}}`. Consumes the reviewed preview; a changed digest/config is rejected. |
| `mcp.oauth.status` | `{id, sessionId, operationId?}` | `{auth, operation?}`. `auth.state` is `not_configured|signed_out|authorized|reauthorization_required|storage_unavailable` plus `generation`, grant id/scopes/expiry when authorized, and `requiredScopes`/`authChallenge` when the live connection recorded a 403 `insufficient_scope`. Local state only; launches nothing. |
| `mcp.oauth.url` | `{id, sessionId, operationId}` | `{authorizationUrl}` — the login link for the pending operation. |
| `mcp.oauth.open` | `{id, sessionId, operationId}` | `{opened: boolean}` — explicit browser launch; failure is reported, never retried silently. |
| `mcp.oauth.cancel` | `{id, sessionId, previewId?, operationId?}` | `{cancelled: boolean}` — retires the pending preview/operation and its loopback listener. |
| `mcp.oauth.forget` | `{id, sessionId, expectedGeneration, revoke?}` | `{auth, remoteRevocation, partial, failures}` — removes local credentials at the reviewed generation; `revoke: true` asks the provider once. Destructive, so the TUI confirms with Cancel as default. |

A 403 `insufficient_scope` is surfaced as sanitized step-up evidence
(`requiredScopes`/`authChallenge`) on `mcp.oauth.status` and in the preview
review; it never widens the requested scopes and never replays the call.
`tool.complete` carries `outcome: "outcome_unknown"` for 401/403/timeout paths
with an exactly-once effect counter.

## Integrated editor workspace (2026-10-15)

Backend-issued workspace identity with bounded file access, revision-checked
saves and structured refusals (plan §11/§19). Workspace events are a separate
family from the chat stream: they carry `workspaceId`/`epoch` and never
`sessionId`/`turnId`, so they cannot enter the transcript reducer.
Request params claiming `actor`/`role` are ignored — the authenticated gateway
token is the only user authority, and workspace identity is minted
server-side. File authorization is resolved-path containment under the
returned `resolvedRoot` (symlinks and `..` are resolved and verified), never a
textual path prefix.

| Method | Params | Result |
|---|---|---|
| `workspace.open` | `{root, trust}` — `trust` is required and boolean | `{workspaceId, clientId, epoch, rootLabel, resolvedRoot, trusted, capabilities}` |
| `workspace.list` | `{workspaceId, path?, cursor?, limit?, includeHidden?}` | `{entries, nextCursor, exclusions, truncated}` or `{refused}` |
| `workspace.read` | `{workspaceId, uri}` | `{uri, text, revision, languageId, lineEnding, encoding, readOnly, sizeBytes}` or `{refused}` |
| `workspace.save` | `{workspaceId, uri, text, expectedRevision?, uiVersion?}` | `{ok: true, revision, savedUiVersion?}` / `{ok: false, conflict: {diskRevision, baseRevision, reason}}` / `{ok: false, refused}` |
| `workspace.documentOpen` | `{workspaceId, uri, languageId?, version, text?, epoch?}` | `{acceptedVersion, serverGeneration, state}` |
| `workspace.documentChange` | `{workspaceId, uri, baseVersion, version, changes, epoch?}` | `{acceptedVersion, resync?}` |
| `workspace.documentClose` | `{workspaceId, uri}` | `{closed, uri}` |
| `workspace.quickOpen` | `{workspaceId, query?, limit?, epoch?, rebuild?}` | `{entries: [{path, name, directory}], total, truncated, reasons, indexing, scanned, stale, workspaceEpoch, exclusions}` or `{refused}` |
| `workspace.quickOpenCancel` | `{workspaceId}` | `{cancelled: boolean}` |
| `workspace.intelligence` | `{workspaceId, operation, uri?, version?, position?, query?, epoch?}` | `{workspaceId, source, uri, documentVersion, serverGeneration, workspaceEpoch, operation, state, freshness, truncated, result}` |
| `workspace.lspStatus` | `{workspaceId}` | `{servers: [{profile, languageId, state, generation, capabilities?, detail?}]}` |
| `workspace.lspControl` | `{workspaceId, action, profile}` (`start\|stop\|restart`) | `{action, profile, state, detail?}` — state changes only, never installation |
| `workspace.close` | `{workspaceId}` | `{closed: true}` |

Revisions are `sha256-hex[0:32]:<size-bytes>`; the client echoes the revision
it read as `expectedRevision`. Reads, lists and saves answer refusals as
`{"refused": {"reason", "message"}}` with a reason in `binary`, `too-large`,
`not-regular`, `unsupported-encoding`, `denied`, `missing` (save adds
`"ok": false`). A save only commits when the current disk revision equals
`expectedRevision` (`expectedRevision` absent means "expect the file to be
missing"); mismatches return the structured conflict and never silently
overwrite. `expectedRevision`-less saves against an existing file conflict.
Cooperative writers share one per-path in-process coordinator; external
writers that ignore the protocol can still race (the revision recheck
immediately before the atomic same-directory temp+replace detects most of
them, but universal compare-and-swap is not claimed).

`workspace.intelligence` is a closed allowlist (`completion`, `hover`,
`definition`, `references`, `symbols`, `diagnostics`) — never a raw LSP method
tunnel. Without an injected language-server manager it answers truthfully with
`state: "missing"`, `freshness: "unavailable"` and `result: null`; no result is
ever fabricated. `workspace.fileChanged` is emitted with
`{type, workspaceId, epoch, uri, revision, origin}` after a confirmed save
(`origin: "save"`); workspace events are not automatically agent prompt
content. Directory pages are bounded (default/max 200 entries; exclusions and
truncation are disclosed), hidden entries are omitted unless `includeHidden`
is set, and default exclusions (`.git`, `node_modules`, `__pycache__`,
`.venv`, `dist`, `build`, `.cache`) are navigation policy — reported and
flagged, not filesystem permissions.

`workspace.quickOpen` searches a bounded recursive index built in the
background (never a blocking full-tree scan). `query` is optional (empty lists
what is indexed so far; max 200 characters) and `limit` is 1–200 (default 50);
results are root-relative `{path, name, directory}` rows ranked by basename —
exact, then prefix, then substring, then subsequence (case-insensitive) — with
stable ties by path length then lexicographically. The index is single-flight
per workspace, cached for 60 s, and rebuilt after expiry or with
`rebuild: true`. Bounds are always disclosed, never silent: 20 000 indexed
files stop the walk (`file-cap`), a 10 s deadline stops it (`deadline`), a
per-directory 5 000-entry cap is named in `reasons` while the walk continues
elsewhere (`directory-entry-cap`), and an unreadable directory marks the
index `unreadable` rather than pretending it is complete; `total` is reported
before the `limit` cut (`result-limit`). While a
scan is still running the answer carries `indexing: true` with the `scanned`
progress count and partial `entries` (the caller re-queries); if the workspace
is reopened mid-scan the retired epoch's results are discarded and answered as
`stale: true` with empty entries. `workspace.quickOpenCancel` cancels the
in-flight scan (`{cancelled}` — false when none runs) and emits no completion
event. Each completed walk also emits `workspace.indexProgress`
`{workspaceId, epoch, scanned, total, done}` (intermediate frames carry
`total: null`), so clients can disclose progress without polling.
Default exclusions are returned in `exclusions`; symlinks are followed only
when their target stays inside the authorized root, and directory cycles
(symlink loops) are visited once.

## Deterministic skills catalog (2026-10-16)

Bounded, deterministic catalog reads over the loaded skill registry
(spec §12.1/§12.2). No model call, embedding, provider, tool execution,
install, or approval mutation is involved. The pre-existing
`skills.list`/`skills.show`/`skills.learn`/`skills.delete`/`skills.curator`
response shapes are unchanged — new fields never leak into them.

| Method | Params | Result |
|---|---|---|
| `skills.search` | `{query?, filters?, limit?, cursor?}` | `{query, filters, limit, browse, candidates, catalogRevision, queryDescriptorRevision, policyRevision, nextCursor, diagnostics}` |
| `skills.preview_route` | `{request, context?}` | `{descriptor, reasons, selection, disclosure, budget, tokenBasis}` |
| `skills.section` | `{skillId, contentRevision?, section?, offset?, budget?}` | `{skillId, contentRevision, sectionId, heading, text, start, end, total, sectionTotal, line, continuation, stale, bound, anchorId, budget, diagnostics}` |

`skills.search` runs the deterministic §9 pipeline over the effective catalog:
`query` is optional (an empty query answers `no_lexical_evidence`, it never
enumerates the catalog); `limit` is 1–50 (default 10); `cursor` is the opaque
`nextCursor` from the previous page. `filters` is a closed object:
`task_family` (a canonical family or a declared schema-v2 value such as
`backend-api`/`deployment`, canonicalized through the search aliases),
`capability` (declared capability), `source` (one provenance string or a list
of at most 8: `builtin-ecc|local|hub|url|learned`), `enabled` (strict boolean)
and `include_excluded` (strict boolean). Disabled skills are never candidates
on the automatic path; they appear — flagged `applicability: "excluded"` with
a `disabled: ...` reason — only when the caller explicitly browses
(`include_excluded: true` or `enabled: false`), which also sets
`browse: true`. Each candidate carries `skillId` (casefolded registry id),
`name`, `contentRevision`, `score` plus named `scoreComponents` (ranking
signals, never calibrated probabilities), `matchedPhrases`,
`matchedCapabilities`, `applicability`, `reasons`, `workflowStages`,
`explanation`, `sourceType`, display-only `trust`
(`bundled|local|external`, never an authorization input), and `enabled`.
Unknown filter keys/values, wrong types, out-of-range limits and malformed
cursors are invalid params (-32602).

`skills.preview_route` is call-free: it builds the TaskDescriptor
(`descriptor`/`reasons`), the deterministic selection plan (`selection.kind`,
`selection.skills`, `selection.steps` — the authoritative planned steps with
stable ids, `catalogRevision`, `taskRevision`) and the §10.3 disclosure plan
(`disclosure` is `DisclosurePlan.to_dict()`: chosen sections with exact
`content_revision` identities, whole-body units, required prerequisites,
omitted sections with continuation locators, unresolved prerequisites,
`missing_context`, `included_tokens`, `token_basis: "char/4"` and bounded
`diagnostics`). `context` is task state only — closed keys `active_class`,
`active_families`, `stack`, `constraints`, `capabilities`, `revision`, `stage`,
`stage_source`, `stage_revision`; the `stage*` facts preview stage-aware
disclosure exactly like the automatic path, and `revision` is reported
pre-incremented as the revision this request would occupy. A preview creates
no turn, calls no provider or embedding, executes no tool, installs nothing,
mutates no approval state and records no operational success.

`skills.section` reads one exact versioned passage. `section` addresses a
declared section id or a parsed heading/anchor; a declared id wins and binds
to its heading anchor (`anchorId`), while an undeclared parsed anchor is
served with a `section-undeclared` diagnostic. `offset` is a character offset
within the section (a raw content offset when no section is given) used for
continuations; `budget` is 1–8000 characters (default 800). Omit
`contentRevision` on the first read; pass the returned `contentRevision` (a
sections content fingerprint — the same revision vocabulary as
disclosure-plan locators) to bind continuations. A stale revision returns
`stale: true` with empty `text` and a `section-stale-content` diagnostic —
never a different passage at the same address. `diagnostics` uses the closed
vocabulary `section-unknown`, `section-undeclared`, `section-stale-content`,
`section-continuation-range`. Unknown skills are `1002`; malformed params are
invalid params (-32602).

The native agent tool `skill_read` gained optional `section` and `revision`
parameters with the same semantics; its legacy character-offset reads
(including the printed `[offset:end/total]` continuation format) are
byte-identical.
